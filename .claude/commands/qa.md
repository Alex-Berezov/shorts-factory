# /qa - проверка сделанного

Аргумент: `$ARGUMENTS`

Порядок жёсткий, шаги не пропускаются и не меняются местами.

## 1. Дифф

```
git rev-parse --abbrev-ref HEAD
git diff --merge-base main --name-status
git diff --merge-base main --stat
git status --porcelain
```

Диффом считаются и незакоммиченные правки, и новые неотслеживаемые файлы. Работа идёт в `main`
без ветки - тогда база сравнения `HEAD`, и дифф - только незакоммиченное; это штатно.

Диффа нет - одна строка «Изменений нет, проверять нечего» и выход; ревьюеров и гейты не звать.

Найди постановку: id задачи и путь к файлу дела из `.claude/.task-current`; в файле дела -
разделы «План», «Решения». Постановку ревьюерам даёшь **одной строкой** (что требовалось), не
пересказ того, как это решалось.

## 2. Кто идёт

**Вызов из `/auto` или без аргумента: набор полный.** Семь ревьюеров, все одним сообщением
(параллельно):

| Ревьюер | Зона | Модель |
| --- | --- | --- |
| `review-correctness` | логика, ошибки, идемпотентность, время, деньги | opus |
| `review-data` | схема, миграции, транзакции, контракты, стоимость, квоты | opus |
| `review-security` | секреты, auth, URL/файлы, инъекции, зависимости | opus |
| `review-conventions` | стандарты, раскладка, дубли, дисциплина диффа | sonnet |
| `review-tests` | посадка, выключенные тесты, подгонка, моки | sonnet |
| `review-architecture` | направление зависимостей, слои, дубли логики, имена, мёртвый код | fable |
| `review-product` | DoD и AC по коду, сценарии оператора, принцип продукта | fable |

Плюс встроенный `code-review` (Skill `code-review`, уровень `high`): правил проекта он не знает,
зато не ограничен чек-листом - логические баги, мёртвые ветки, дублирование.

Сокращать набор нельзя ни по размеру диффа, ни ради скорости: дифф никто не читает глазами.
Исключение одно - **ручной вызов** владельцем с `zones=…`: тогда идут только названные плюс
`code-review`, и в отчёте первой строкой сказано, что набор сокращён и кем.

Дифф только в `docs/**` и `tasks/**` - ревьюеров не звать, только `review-product` (расхождение
документа со спецификацией - его находка) и `code-review`.

Дифф трогает `.claude/**` - отдельным заданием `review-conventions` и `review-tests` дай файлы
обвязки с пояснением: это код хуков и правил на Node, не продукт; хук обязан уметь запрещать,
и правка хука закрывается пробой на отказ **и** на пропуск (см. `docs/60_HARNESS.md`).

## 3. Пакет каждому ревьюеру

Одинаковый для всех:

- id задачи и путь к файлу дела (план и решения там; DoD - в документе эпика по ссылке из шапки);
- список изменённых файлов со статусами A/M/D;
- дифф `git diff --merge-base main` (велик - `--stat` и список файлов, полный дифф ревьюер
  добирает сам);
- постановка одной строкой.

Чего в задании быть не должно: твоих объяснений, почему код написан так; оценки серьёзности;
просьбы «проверь только вот это». Ревьюер идёт в свежем контексте и не должен узнать от тебя,
как шла работа.

Отчёт «нарушений не нашёл» принимается только с разбором чек-листа (какие пункты неприменимы
и почему). Пустой отчёт без разбора - верни ревьюера: «пройди чек-лист по пунктам».

## 4. Сводная таблица - в файл дела

Раздел `## Ревью <дата>` в файле дела. Одна таблица, строки от блокеров к придиркам:

| Серьёзность | Файл:строка | Что не так | Правило | Что сломается | Кто нашёл |
|---|---|---|---|---|---|

- Одна и та же находка от разных ревьюеров - одна строка, все имена в «Кто нашёл».
- Расходятся в серьёзности - бери высшую.
- **Находка, внесённая самой правкой, - блокер, кто бы её ни нашёл**, включая
  `review-architecture` (у него своих блокеров нет). Проверка: виден ли дефект в текущем диффе.
- Находка без правила (пункт чек-листа, правило хука, раздел документа, DoD, урок `L-0NN`,
  решение из `DECISIONS.md`) в таблицу не идёт - кроме находок `review-product`, у которых
  вместо правила цитата обещания.
- Формулировку не смягчай. Не согласен - строка остаётся, возражение отдельной строкой под ней;
  спор решает `techlead`, не ты.
- Блок `Предложения` от `review-architecture` и «Техдолг рядом» от всех - отдельным разделом
  под таблицей; оркестратор `/auto` переносит их в `docs/TECH_DEBT.md`.

## 5. Гейты

```
node .claude/hooks/gates.js
```

Одна команда, без сужений. Вывод - в файл дела как есть (строки и код возврата). Пересказ
словами вместо вывода не принимается ни при каком результате.

## 6. Отметка

```
node -e "const fs=require('fs'),p='.claude/.qa-state',H=require('./.claude/hooks/diff-hash.js');H.markQa();let s=JSON.parse(fs.readFileSync(p,'utf8'));s.edits=0;s.strayFiles=[];fs.writeFileSync(p,JSON.stringify(s,null,2));console.log('файлов на ревью:',s.qaFiles.length,'| отпечаток:',s.qaDiffHash.slice(0,8))"
```

Отметку ставит `markQa()` из `diff-hash.js` - она пишет `lastQa`, `qaDiffHash` и `qaFiles`
(что ревьюеры видели). Ставить её руками или до шагов 2–5 нельзя: замок коммита сверяет
отпечаток с текущим диффом, и отметка от другого набора файлов его не откроет.

## 7. Итог в чат

Не больше восьми строк: сколько файлов в диффе; в каком режиме шли ревьюеры (полный набор /
сокращён кем и до чего); сколько блокеров, замечаний, придирок; итог гейтов одной строкой
с кодом возврата; путь к делу.

Есть блокеры - перечисли их одной строкой каждый и остановись: правки в этом ходу не начинай
(в `/auto` их делает шаг 6 через `/fix`). Блокеров нет - скажи это и назови число замечаний.
