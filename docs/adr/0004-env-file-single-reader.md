# ADR-0004: корневой `.env` монтируется в контейнеры и читается тем же `@sf/config`, что под `pnpm dev`

Дата: 2026-10-10   Статус: принято   Задача: E0-11

## Контекст

Корневой `.env` читают два пути: `pnpm dev` на хосте (`bootstrapEnv` -> `util.parseEnv`
в `@sf/config`) и контейнеры полного стека. E0-11 сначала отдавал файл контейнерам через
`env_file` Compose, и пять заходов ревью подряд находили новое расхождение двух парсеров:
формат по умолчанию раскрывал `$NAME` внутри значения (пароль с `$` короче в контейнере),
`format: raw` оставлял кавычки и хвостовой `# комментарий` частью значения (пароль
из 14 символов в кавычках проходил пол 16), правила грамматики в `load-env.ts` закрывали
по одному классу (ведущая кавычка, `#`, `${`), а обратные кавычки (W1, круг 6) прошли мимо.
Каждая заплата описывала чужой парсер ещё одним правилом - класс не закрывался по построению.
Решение владельца Р9 (стоп 3): один парсер на обоих путях; исполнение - Р10 техлида.

## Решение

- `infra/docker-compose.app.yml`: у `migrate`, `api`, `worker`, `web` нет `env_file`;
  один anchor `x-env-mount` - bind `../.env` -> `/repo/.env`, `read_only: true`,
  `bind: { create_host_path: false }`.
- `/repo/.env` - это `rootEnvFilePath` из `packages/config/src/paths.ts` во всех образах:
  api, worker и migrate работают из `/repo/...` (`WORKDIR /repo` при сборке и та же
  раскладка в рантайме), web - из `/app`, но путь вычислен при сборке под `/repo` и запечён
  webpack-ом в бандл. Доказательство: в образе web
  `grep -c "file:///repo/packages/config/src/paths.ts" /app/apps/web/.next/server/middleware.js`
  = 1 (`tasks/2026-10-10-E0-11.md`, «Прогоны: круг 7»). Кода в `@sf/config` нет,
  переменной пути нет.
- `environment` побеждает файл: `mergeEnvFile` (`env-file.ts`) заполняет только ключи,
  которые процесс оставил пустыми. Поэтому адреса сети, `MEDIA_DIR`, `NODE_ENV`, закреплённый
  `API_PORT` из `environment` действуют, а отпечаток сборки (`ENV APP_VERSION`/`GIT_COMMIT`
  образа api) не гасится пустой строкой `.env`.
- Правила грамматики значений в `load-env.ts` (`ENV_GRAMMAR_RULES`) и их тесты удалены:
  расхождения, которые они ловили, больше не существует.
- Гейт `compose`, правило 10 (`scripts/compose-rules.mjs`): `env_file` нет ни у одного
  сервиса; у `migrate`/`api`/`worker`/`web` есть bind-том с `source` = `.env` проекта,
  `target: /repo/.env`, `read_only: true`, `create_host_path: false`. Контракт
  `paths.ts` | Dockerfile | compose стережёт гейт.
- Корневой `.env` остаётся файлом интерполяции Compose (`${WEB_PORT:-3000}` берётся оттуда);
  DoD-команда `docker compose up --build` из корня не меняется. Свою грамматику Compose
  применяет только для интерполяции, в контейнеры эти значения не идут, но предупреждения
  и ошибки печатают значение: `$имя` в значении без одинарных кавычек -
  `The "<имя>" variable is not set` (W7), незакрытая `${` - `Invalid template: "<значение>"`
  (W8). Это документировано в `infra/README.md` вместе с обходом
  `docker compose --env-file .env.example up --build`.
- Права: в контейнерах процесс - `node` (uid 1000). На Linux-хосте `.env` должен быть
  читаем этим uid; иначе `readEnvFile` получает `EACCES` и бросает (не молчит), `migrate`
  останавливает стек.

## Альтернативы

- `env_file` с форматом по умолчанию - раскрывает `$NAME` внутри значения; порча невидима
  конфигу, значение приходит уже изменённым.
- `env_file` с `format: raw` + правила грамматики в `load-env` (Р6-Р8) - пять заходов,
  каждый находил новый класс расхождения (последний - обратные кавычки); правила описывают
  чужой парсер и не сходятся с ним по построению.
- Переменная пути (`SF_ENV_FILE`) или `--env-file` в DoD-команде - лишний контракт
  и изменение команды владельца; `/repo/.env` уже единственный путь во всех образах.
- `COMPOSE_DISABLE_ENV_FILE` / отключить интерполяцию - тогда `${WEB_PORT}` из `.env`
  перестаёт работать, а DoD-команда требует флага.

## Последствия

- Значение в `.env` одно и то же под `pnpm dev` и в контейнере: кавычки допустимы и срезаются,
  значение без кавычек кончается на первом `#` - на обоих путях одинаково.
- web получает весь `.env`, как под `pnpm dev`; сужение окружения по сервисам - E1-12
  (`docs/TECH_DEBT.md`).
- Нельзя: возвращать `env_file` в сервисы приложения, менять `WORKDIR /repo` сборки или
  `target` монтирования порознь - гейт `compose` и `rootEnvFilePath` должны указывать
  в одно место.
- `create_host_path: false` остаётся в compose и в правиле 10 гейта. На Linux-движке стек без
  `.env` не стартует и каталога не создаёт - на Linux не проверено (проверка - строка
  `docs/TECH_DEBT.md`, E1-12). Docker Desktop (Windows) опцию не передаёт: создаёт пустой
  каталог `.env` в копии без файла, `migrate` падает `EISDIR`, стек не стартует; поведение
  описано в `infra/README.md`. Код `@sf/config` не меняется.
- Остаётся: интерполяционный проход Compose по корневому `.env` (W7/W8) - документация
  и обход `--env-file .env.example`.
- Откат: anchor `x-env-mount` заменить на `env_file`, правило 10 - на прежнее; кода
  `@sf/config` откат не касается.
