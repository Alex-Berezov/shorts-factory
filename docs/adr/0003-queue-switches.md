# ADR-0003: `queues.enabled` выражается паузой очереди BullMQ, и ставит её только воркер

Дата: 2026-09-10   Статус: принято   Задача: E0-08

## Контекст

`app_setting.queues.enabled` - одна JSONB-строка с переключателем на каждую очередь реестра
`QUEUE_NAMES`; засеяна в E0-04 значениями `true` (решение PM Р8). Что означает `false`
в рантайме и кто читает ключ, осталось открытым с E0-04 (`docs/TECH_DEBT.md`, 06.09.2026):
без ответа оператор видит выключатель, который никто не читает, а эпик с платным
обработчиком рассчитывает на предохранитель, которого нет.

К этому же ключу тянутся две будущие задачи: `/system/queues` с кнопками «пауза/пуск»
(E13-02) и автопауза очередей при исчерпании квоты YouTube (E1-08). Если каждая заведёт
свой механизм, состояние очереди будет складываться из трёх источников, и ни один
не будет знать про два других.

## Решение

`false` означает **паузу очереди BullMQ** (`queue.pause()`), `true` - `resume()`.

- Состояние применяется при старте воркера и переприменяется таймером раз в 60 секунд
  в `apps/worker/src/runtime.ts` - **не внутри джоба `system.heartbeat`**: джоб подчиняется
  тому же переключателю, который читает, и `false` на `system.heartbeat` остановил бы сам
  ресинк.
- `pause()`/`resume()` зовёт единственный модуль - `apps/worker/src/lib/queue-switches.ts`.
  Прямая пауза из api или из скрипта запрещена: ресинк снимет её в течение минуты.
  Кто хочет паузу - пишет её в `app_setting`.
- Схема значения одна и лежит в `@sf/core` рядом с реестром: `QueueSwitchesSchema`
  (`z.record(z.string(), z.boolean())`), ключ - `QUEUE_SWITCHES_KEY`. Seed пишет, воркер
  читает, api E13-02 пишет.
- Реакция на несогласованность:
  - строки `queues.enabled` нет вовсе - воркер **не стартует** с подсказкой `pnpm db:seed`
    (пустая строка означает незасеянную базу, а не «всё включено»);
  - значение не разбирается схемой - то же самое при старте, `error` и нетронутое
    состояние на тике;
  - ключ вне `QUEUE_NAMES` (переименованная очередь) - `warn` и игнор; такие ключи удаляет
    `seedAppSettings` (`pruneQueueSwitches`), и только для строки `queues.enabled`;
  - очереди нет в строке - `warn`, состояние очереди не трогается (умолчание «включено»
    молча отменило бы паузу оператора);
  - состояние уже совпадает - ничего не делается, иначе тик раз в минуту был бы `RENAME`
    по каждой очереди раз в минуту.

## Альтернативы

- **Не создавать `Worker` для выключенной очереди.** Одна ветка в `runtime.ts`, но
  переключатель действует только после рестарта процесса, а в BullMQ очередь при этом
  выглядит как «есть работа, никто не берёт» - неотличимо от зависшего воркера.
- **Не ставить джобы (проверка в `enqueue`).** Ключ пришлось бы читать и в api, и в воркере,
  с кэшем; выключенная очередь теряла бы события вместо того, чтобы копить их - для
  `radar.*` это дыра в данных, которую нечем закрыть задним числом.
- **Чистка неизвестных ключей в воркере, а не в seed.** Запись из процесса, который только
  читает настройку, и гонка между несколькими воркерами; `pnpm db:seed` и так выполняется
  при каждом деплое (E0-11).

## Последствия

- Оператор меняет переключатель - эффект наступает в течение минуты без рестарта; состояние
  видно в Redis как `paused` и совпадает с тем, что показывает и переключает E13-02.
- E13-02 (`POST /system/queues/:name/pause|resume`) и E1-08 (автопауза по квоте) выражают
  намерение записью в `app_setting`: E1-08 - своим ключом, композиция значений остаётся
  в `queue-switches.ts`. Второго механизма паузы в системе нет. Контракт второго ключа
  (решение техлида 10.09.2026, пишет его E1-08):
  - ключ `queues.autopaused` в `app_setting`, форма значения - `Record<очередь, причина>`
    (причина сегодня одна - `"youtube_quota"`, Data API; E7-03 заводит вторую -
    `"youtube_analytics_quota"`, Analytics API, отдельно от Data API, чтобы дневной сброс не
    снимал не ту квоту; позже `"gemini_budget"`, `"tts_budget"`), схема `QueueAutopauseSchema`
    и константа ключа - в `@sf/core` рядом с `QueueSwitchesSchema`;
  - эффективное состояние очереди - `enabled[q] === true && !(q in autopaused)`; считает его
    только `queue-switches.ts`, он же единственный, кто зовёт `pause()`/`resume()`;
  - `system.quota-reset` удаляет из `queues.autopaused` только записи с причинами
    `youtube_quota` (Data API, E1-08) и `youtube_analytics_quota` (Analytics API, E7-03) -
    обе квоты одного проекта Google обновляются в одном и том же окне; `queues.enabled` не
    трогает вовсе: ручная пауза оператора переживает ночной сброс квоты;
  - `POST /system/queues/:name/resume` оператора снимает обе записи очереди (`enabled[q] = true`
    и удаление её из `autopaused`) - иначе кнопка не работает, пока держится автопауза;
  - отсутствие строки `queues.autopaused` - тот же исход, что у `queues.enabled` (воркер
    не стартует с подсказкой `pnpm db:seed`), поэтому seed пишет её со значением `{}`.
- Ручная пауза мимо настройки живёт не дольше минуты. Это цена одного источника правды.
- Выключенная очередь копит джобы в `waiting`; ретеншн и разбор накопленного - тема E13.
- Служебные очереди тоже имеют переключатели: `system.heartbeat: false` погасит
  `worker:heartbeat`, и `/system` покажет «воркер лежит». Это видимое последствие действия
  оператора, а не дефект; ресинк от этого не страдает - он живёт в `runtime.ts`.
- Откат: снять таймер и вызовы `pause()`/`resume()` вместе с `queue-switches.ts` и чисткой
  в seed; оставшиеся флаги `paused` в Redis снимаются `queue.resume()` по очередям, ключ
  в базе не трогается.
