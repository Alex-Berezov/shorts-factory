# ADR-0008: DLQ - отдельная очередь `system.dlq`, куда копируется окончательно упавший job

Дата: 2026-10-10   Статус: принято   Задача: E0-13 (решение 4 эпика E0; реализовано в E0-08, E0-10)

## Контекст

У BullMQ нет встроенной очереди мёртвых писем: job, исчерпавший `attempts`, остаётся записью
`failed` в своей очереди, пока её не вытеснит `removeOnFail`. С E1/E2 такой job - потраченная
квота или оплаченный вызов, и оператору нужно одно место, где видны все окончательные провалы
всех очередей, с причиной и полезной нагрузкой, переживающее чистку исходных очередей.

## Решение

- **Копия, а не перенос.** Обработчик события `failed` каждого `Worker`, то есть каждой
  очереди с процессором (`createFailedHandler` / `createDlqWriter` в `apps/worker/src/lib/dlq.ts`,
  подключение - `apps/worker/src/runtime.ts:193-200`), при окончательном
  провале добавляет копию в очередь `system.dlq`. Окончательный провал - `attemptsMade >=
  opts.attempts` или `UnrecoverableError` (`isFinalFailure`); промежуточные попытки
  только пишут `warn` «job failed, will retry».
- **Исходная запись `failed` остаётся** в своей очереди: общая политика
  `DEFAULT_JOB_OPTIONS` (`apps/worker/src/lib/job-policy.ts`) - `attempts: 5`, экспоненциальный
  `backoff` от 5 с, `removeOnComplete: { count: 1_000 }`, `removeOnFail: { count: 1_000 }`.
- **Запись DLQ сама не стареет и не повторяется**: копия ставится с `attempts: 1`
  и `removeOnFail: false`.
- **Поля записи** - `DlqRecord`: `queue`, `jobId`, `name`, `data`, `failedReason`, `stacktrace`,
  `attemptsMade`, `failedAt` (ISO). Поля явные, id записи не разбирается
  (`docs/DECISIONS.md`, 10.09.2026, E0-08).
- **id записи детерминированный**: `jobIds.dlqEntry(queue, originalId, dlqTimestamp(job.timestamp))` =
  `dlq/<очередь>/<исходный id, ":" → "@">/<timestamp>` (ADR-0009). Второе событие `failed`
  того же экземпляра (воркер перезапущен, пока job умирал) не даёт второй записи.
- **Клапан `0` принят осознанно.** `job.timestamp` воркер получает из Redis через `parseInt`
  от переданного `opts.timestamp`. Реальные входы: отрицательное целое, NaN, целое, потерявшее
  точность в Lua (14 значащих цифр: `2**53` приходит как `9`); `Infinity` и значения за
  `MAX_SAFE_INTEGER` до `dlqTimestamp` не доходят (проверено по `storeJob.lua` и `job.js`
  BullMQ 5.81.4, уточнено 11.10.2026, круг 5). Такой вход `dlqEntry` отверг бы, и копия
  потерялась бы в `catch`, поэтому `dlqTimestamp` превращает его в `0`. Цена: два провала
  одного исходного id с «грязными» моментами получают один id записи DLQ, вторая копия тихо
  дедуплицируется BullMQ. Это приемлемо: `0` виден в id, а достижим только через ручной
  `opts.timestamp`, которого в коде нет (E0-13, решение техлида 11.10.2026, 9).
- **У `system.dlq` нет процессора**: очереди нет в `JOB_PROCESSORS`
  (`apps/worker/src/jobs/index.ts`), записи читает оператор. В E0 `/system` показывает число
  записей DLQ и счётчики исходных очередей (`GET /system/status`, поле `dlq: { size }`); просмотр
  записей, retry и discard - E13-02.
- **Сбой записи в DLQ не роняет процесс**: обработчик никогда не отклоняет промис (ошибка
  пишется в лог), а остановка воркера дожидается начатых копий (`DlqWriter.drain()`).
- Очередь `system.dlq` - в общем реестре `QUEUE_NAMES` и получает переключатель
  `queues.enabled`, как все очереди; смысл переключателя - ADR-0003.

## Альтернативы

- **Только записи `failed` в исходных очередях** - вытесняются `removeOnFail`, разбросаны
  по 28 очередям, после чистки причина провала теряется.
- **Таблица в Postgres** - вторая запись при отказе Redis, которая сама может упасть; лишняя
  миграция до E13, где решается, что оператор делает с записью.
- **Перенос вместо копии** (удалить исходный `failed`) - оператор, уже смотрящий на запись
  в очереди, теряет её из-под рук.

## Последствия

- Каждый job, созданный через `defineJob`, попадает в DLQ без кода в самом job.
- Retry из DLQ (E13-02) строит id тем же примитивом, что `dlqEntry`; разбирать id обратно
  нельзя - поля записи и есть источник.
- Счётчик DLQ растёт без ограничения, пока E13 не даст discard: `removeOnFail: false`
  выбран сознательно.
