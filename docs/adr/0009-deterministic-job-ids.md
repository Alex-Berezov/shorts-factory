# ADR-0009: идемпотентность постановки через детерминированный `jobId` из билдеров `@sf/core`

Дата: 2026-10-10   Статус: принято   Задача: E0-13 (решение 5 эпика E0; реализовано в E0-04, E0-05, E0-08, E0-13)

## Контекст

Джобы ставят cron, оператор и другие джобы, иногда одновременно и повторно: два тика
планировщика в одном интервале, перезапуск воркера посреди постановки, повторный клик.
Каждая лишняя постановка с E1 - потраченные units YouTube или оплаченный вызов Gemini.
BullMQ игнорирует второй `add` с тем же custom id, пока запись job в Redis, - значит, id должен
строиться из смысла job одинаково везде, где job ставится.

## Решение

- **Каждый job объявляет `jobIdFrom(payload)`** в `defineJob` (`apps/worker/src/lib/define-job.ts`,
  `JobSpec.jobIdFrom`); `enqueue` валидирует payload его Zod-схемой, строит id и передаёт его
  в `queue.add`. Job, чья идентичность - момент времени (heartbeat), получает часы параметром
  определения, а не читает их в `jobIdFrom`.
- **id строят только именованные билдеры `jobIds.*`** в `packages/core/src/domain/job-ids.ts`
  (`radarSync`, `radarScore`, `systemSmoke`, `systemHeartbeat`, `dlqEntry`); каждый эпик
  добавляет туда свой. Вызов `jobId()` прямо из процессора - находка ревью: так расходится формат.
- **Реестр имён очередей** `QUEUE_NAMES` / `QueueName` живёт рядом, в
  `packages/core/src/domain/queues.ts`: имена нужны воркеру (`Queue` на каждое имя) и `@sf/db`
  (переключатели `queues.enabled` в seed), а ниже обоих только `@sf/core`
  (`docs/DECISIONS.md`, 06.09.2026, E0-04).
- **Формат** `<префикс>/<часть>/<часть>...` - сегменты склеиваются через `/`, не `:`: BullMQ 5
  отвергает custom id с `:` (`Job.addJob → validateOptions`), кроме случая ровно трёх сегментов,
  и обещает полный запрет в следующем мажоре.
- **Правила части** (`segment()`):
  - строка не пустая и не содержит `/` и `:` - иначе `ValidationError`; значение, которому
    нужен разделитель, кодирует билдер: версия промпта пишется `<name>@<version>`
    (`dna.full@1.0.0`), момент времени - epoch ms;
  - число - только безопасное целое ≥ 0 (`Number.isSafeInteger(value) && value >= 0`),
    иначе `ValidationError` с позицией части. Дробное (`1.5`), отрицательное, `1e21`
    (печатается `1e+21`) и целое больше `Number.MAX_SAFE_INTEGER` в id не попадают: id
    зависел бы от того, как печатается число, и два вызова с одним смыслом получили бы два id
    (E0-13, `docs/DECISIONS.md` 10.10.2026; посадка - `packages/core/test/job-ids.test.ts`).
- **id из одних цифр отвергается** (`finalize`): BullMQ отвечает на такой id «Custom Id cannot
  be integers» уже в рантайме, внутри `queue.add`.
- **Готовый id внутри другого id** (`embedJobId`, только для `jobIds.dlqEntry`) не проходит
  через `segment()`: в нём уже есть `/`, а id планировщика BullMQ - `repeat:<schedulerId>:<millis>`.
  Кодируется только `:` → `@`; `/` вкладывается как есть. Результат необратим и не разбирается:
  запись DLQ несёт поля явно (`docs/DECISIONS.md`, 10.09.2026, E0-08; ADR-0008).
  Хвост id записи DLQ - нормализованный timestamp задания (`dlqTimestamp` в
  `apps/worker/src/lib/dlq.ts`: безопасное целое не меньше 0 проходит как есть, всё остальное
  даёт 0). Реальные входы: отрицательное целое, NaN, целое, потерявшее точность в Lua
  (14 значащих цифр: `2**53` приходит как `9`); `Infinity` и значения за `MAX_SAFE_INTEGER`
  до `dlqTimestamp` не доходят (BullMQ восстанавливает `timestamp` через `parseInt`, дробь не
  доходит; уточнено 11.10.2026, круг 5). Так `opts.timestamp` не теряет копию;
  склейка таких моментов в один id - ADR-0008 (E0-13, решения техлида 11.10.2026, 8, 9 и 10).
- `jobId` содержит `/`, поэтому в URL передаётся только query-параметром, сегментом пути - никогда.

## Альтернативы

- **id по умолчанию от BullMQ (счётчик)** - дубль постановки не отличим от нового job.
- **Проверка «есть ли такой job» перед `add`** - гонка между проверкой и вставкой; BullMQ
  уже держит уникальность id атомарно.
- **Склейка через `:`** - отвергается BullMQ 5 (см. выше).
- **`String(value)` для любого конечного числа** (так было до E0-13) - формат id зависел
  от представления числа.

## Последствия

- id защищает от дубля, только пока запись job в Redis: после вытеснения по
  `removeOnComplete`/`removeOnFail` (по 1 000 записей на очередь, ADR-0008) тот же id можно
  поставить снова. Поэтому обработчик всё равно обязан быть безопасным при повторе -
  идемпотентность записи держит уникальный индекс в БД (урок L-007), не id.
- Пересчёт с тем же смыслом (например, скоринг после смены весов) требует сегмента версии
  или времени в id: иначе BullMQ молча вернёт старый job (`docs/TECH_DEBT.md`, 07.09.2026,
  `jobIds.radarScore` → E1-06).
- Формат держат юнит-тесты `packages/core/test/job-ids.test.ts` (ожидания - строковые
  литералы, не вызов того же билдера) и `apps/worker/test/job-id.int.test.ts`, который
  прогоняет `jobIds.*` через настоящий `queue.add`.
