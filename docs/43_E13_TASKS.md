# E13. Dashboard shell и системная страница — декомпозиция на задачи

_Дата: 2026-09-05. Источник: `20_TZ_HIGH_LEVEL.md` (E13), `10_SYSTEM_DESIGN.md` §8 (наблюдаемость, безопасность, стоимость), `02_PRE_DEVELOPMENT_CHECKLIST.md` §B2, §G. Статус: ✅ декомпозирован. Сквозной эпик: базу даёт E0-09/E0-10, остальное наполняется по мере эпиков; задачи ниже можно брать в любой момент после E0._

## Цель эпика

Единая внутренняя оболочка приложения.

**AC эпика:** все модули доступны из одной навигации; расход бюджета и квот виден ежедневно; превышение лимитов заметно сразу.

## Что уже есть (после E0)

- Layout с навигацией по разделам, basic auth (E0-10); `/system` с health, heartbeat, очередями, DLQ count, расходом за день/месяц (E0-09/E0-10); `/system/status` контракт; алерты как ключи `app_setting.alerts.*` (E1-08, E2-09, E10-08); пауза/резюм очередей (E1-08).

## Архитектурные решения E13

1. **Алерты — таблица, а не ключи в `app_setting`.** `alert { id, kind, severity: info | warn | critical, title, payload jsonb, source, created_at, resolved_at, resolved_by, dedupe_key }`. Продюсеры (квота, бюджет, DLQ, ошибки синка, OAuth, застрявшие job'ы) пишут через `alertsRepo.raise(kind, dedupeKey, …)` — повторное срабатывание обновляет существующий открытый алерт, а не плодит новые. Ключи `app_setting.alerts.*` из E1/E2/E10 мигрируют сюда (E13-04), пока живут параллельно.
2. **Управление очередями — из UI, с подтверждением.** Pause/resume очереди, retry/discard job'а из DLQ, запуск repeatable-job вручную. Все действия логируются в `audit_log { actor, action, target, payload, created_at }` — один оператор, но история «кто что нажал» нужна для разборов.
3. **История расходов — витрина `api_usage_daily`.** Ежедневный job агрегирует `api_usage_log` по `(day, provider, operation)` → units, tokens, $; графики за 30/90 дней читают витрину, не сырые строки. Прогнозы (до конца дня/месяца) — линейная экстраполяция по текущему темпу (E1-08 уже делает для units).
4. **Внешние условия — ручной чек-лист с датами.** `external_condition { key, title, status: unknown | pending | enabled | failed, checked_at, note }`: Advanced Features, Multi-Language Audio протестирован, OAuth-приложение в production, монетизация. Читается E11-05 (блокировка шага кастомного аудио) и `/system`.
5. **Auth остаётся basic, но с защитой.** Rate-limit на неуспешные попытки (Redis, 10/мин/IP → 429), security-заголовки (Next `headers()` + `@fastify/helmet`), `Cache-Control: no-store` на всех страницах, `ADMIN_PASSWORD` минимум 16 символов в production (проверка в `@sf/config`). Сессионные куки и пользователи — не делаем (System Design §2: одного admin-логина достаточно).
6. **Навигация отражает статус.** Бейджи: Inbox — число `new`; System — число открытых `critical/warn` алертов и DLQ; Publishing — items `failed`. Активный раздел, хлебные крошки на вложенных страницах (идея → бриф/скрипт/пакет/локализация/публикация как вкладки одной сущности).

## Изменения схемы БД (миграция `0013_system`)

| Таблица | Изменение |
|---|---|
| `alert` | новая (решение 1), индекс `(resolved_at) where null`, unique `(dedupe_key) where resolved_at is null` |
| `audit_log` | новая (решение 2) |
| `api_usage_daily` | новая (решение 3), unique `(day, provider, operation)` |
| `external_condition` | новая (решение 4), сид ключей |
| `app_setting` | `system.alert_thresholds` (DLQ size, stuck job minutes, sync error streak), `system.usage_retention_days` (сырые логи — 90 дней, витрина — бессрочно) |

## Задачи

Суммарно ≈ 5.5–6 дней.

### E13-01. Навигация и оболочка

**Сделать:**
- Разделы: Radar / Inbox / Ideas / Production / Analytics / Experiments / Localization / Publishing / System — порядок по пайплайну; активное состояние; сворачиваемая боковая панель; мобильная версия (нижняя навигация для чек-листов E6).
- Бейджи (решение 6) через один лёгкий эндпоинт `GET /system/nav-badges` (кэш 15 с).
- Страница идеи как контейнер с вкладками: Карточка / Ресёрч / Скрипт / Пакет / Локализация / Публикация / Видео (аналитика) — вкладки появляются по готовности эпиков, до этого скрыты.
- Глобальные состояния: баннер критических алертов вверху всех страниц; баннер «YouTube не подключён» до OAuth.

**DoD:** все реализованные модули доступны за один клик; бейджи отражают состояние; на телефоне навигация удобна.
**Оценка:** 1 д. **Зависимости:** E0-10.

### E13-02. Очереди, планировщики, DLQ — просмотр и управление

**Сделать:**
- `GET /system/queues` (по очереди: waiting/active/delayed/failed/paused, скорость за час), `POST /system/queues/:name/pause|resume` — **запись `queues.enabled[<очередь>]` в `app_setting`, а не `queue.pause()`**: паузу ставит воркер по этой настройке (ADR-0003), прямая пауза из api была бы снята ресинком в течение минуты; `resume` снимает обе записи очереди — `queues.enabled[<очередь>] = true` и её запись в `queues.autopaused`, иначе кнопка не действует, пока держится автопауза по квоте (E1-08); ответ отдаёт состояние настройки, UI показывает «применится в течение минуты», а `GET /system/queues` показывает, кто поставил паузу: оператор (`queues.enabled`) или автопауза с её причиной (`queues.autopaused`), `GET /system/schedulers` (repeatable-jobs с cron, TZ, next run, last run/статус), `POST /system/schedulers/:key/run-now`.
- `GET /system/dlq` (пагинация, фильтр по очереди, payload, ошибка, попытки), `POST /system/dlq/:id/retry` (повторная постановка в исходную очередь с новым id `<исходный jobId>/<requestedAtMs>` — момент повтора в epoch ms; суффикс дописывает к готовому id хелпер этой задачи `jobIds.dlqRetry(originalId, requestedAtMs)`: исходный id уже прошёл `segment()` при первой постановке, поэтому через `jobId(prefix, ...parts)` с исходным id как частью такой id не строится), `POST /system/dlq/:id/discard`, `POST /system/dlq/discard-all?queue=`.
- `audit_log` на все действия; UI `/system/queues`, `/system/dlq` с подтверждениями и просмотром payload/stack.
- Детектор застрявших job'ов (`active` дольше `stuck_minutes`) → алерт.
- Тесты API на фейковых очередях.

**DoD:** упавший job можно разобрать и перезапустить из UI за минуту; действия в `audit_log`.
**Оценка:** 1.5 д. **Зависимости:** E0-08, E0-09.

### E13-03. История расходов и прогнозы

**Сделать:**
- Миграция `0013_system` (все таблицы); job `system.usage-rollup` (ежедневно, + инкрементально за текущий день каждые 15 мин) → `api_usage_daily`; ретенция сырых логов.
- `GET /system/usage?from&to&provider` (витрина + сегодня из сырых), `GET /system/usage/forecast` (день: units YT, $ Gemini; месяц: $ TTS, $ всего).
- UI `/system/usage`: графики 30/90 дней по провайдерам (Recharts), линии лимитов, таблица по операциям (что именно ест бюджет: `video_analysis`, `research_grounded`, `synthesize`…), сумма за 3 месяца против бюджета проекта $500–700.
- Тесты агрегатов и прогноза.

**DoD:** видно, куда уходят деньги по дням и операциям; прогноз месяца совпадает с фактом ±15 %.
**Оценка:** 1 д. **Зависимости:** E0-09.

### E13-04. Центр алертов

**Сделать:**
- `alertsRepo.raise/resolve`, дедупликация (решение 1); продюсеры: квота YT (E1-08), бюджет Gemini (E2-09), бюджет TTS (E10-08), рост DLQ выше порога, застрявшие job'ы, серия ошибок синка канала (E1-03), OAuth `invalid_grant` (E7-01), неудачная публикация (E11-03), не оценённые дабы старше N дней (E9-02) — переводятся с `app_setting.alerts.*` на таблицу.
- `GET /system/alerts?status=open|resolved`, `POST /system/alerts/:id/resolve`, `POST /system/alerts/:id/snooze { until }`.
- UI `/system/alerts` + баннер (E13-01) + бейдж; каждая карточка алерта — ссылка на место действия (очередь, канал, видео).
- Тесты дедупликации и авторезолва (квота сброшена → алерт закрывается сам).

**DoD:** превышение любого лимита видно на всех страницах в течение минуты; закрытые алерты хранят историю.
**Оценка:** 1 д. **Зависимости:** E13-03.

### E13-05. Внешние условия

**Сделать:**
- Сид `external_condition`: `advanced_features`, `multi_language_audio_tested`, `oauth_app_production`, `monetization`, `auto_dubbing_review_all_languages`; `GET/PATCH /system/conditions/:key { status, note }`.
- UI-блок на `/system` с датой последней проверки и подсказкой, где проверять (пути из чек-листа §B2/§G); напоминание-алерт `info` раз в 2 недели «проверить Advanced Features», пока `pending`.
- E11-05 читает `advanced_features.status`.

**DoD:** статусы ведутся в системе; E11 реагирует на `enabled`.
**Оценка:** 0.5 д. **Зависимости:** E0-06.

### E13-06. Здоровье интеграций

**Сделать:**
- `GET /system/integrations`: по провайдерам — ключ задан (без раскрытия), последний успешный вызов (из `api_usage_log`), последняя ошибка (из алертов/логов), для Google — статус OAuth, scopes, email, канал; версия приложения/коммит, uptime api/worker, версия схемы БД (последняя миграция).
- UI-блок на `/system`; кнопка «проверить сейчас» — дешёвый ping каждого провайдера (например `channels.list` 1 unit, Gemini `countTokens`).
- Тесты.

**DoD:** одна страница отвечает на вопрос «всё ли подключено и живо».
**Оценка:** 0.5 д. **Зависимости:** E0-09, E7-01.

### E13-07. Защита доступа

**Сделать:**
- Rate-limit неуспешных basic-auth в web middleware и api (Redis), 429 с `Retry-After`; лог попыток.
- Security-заголовки (CSP для внутреннего приложения — строгая, с разрешением только своих источников; `frame-ancestors 'none'`; `no-store`), `@fastify/helmet`.
- `ADMIN_PASSWORD` ≥ 16 символов в production (E0-03 схема), предупреждение на `/system`, если действующий `ADMIN_PASSWORD` короче 16 символов (значение пароля не показывать — только факт «короче 16»). Предупреждение осязаемо только вне production: в production конфиг с коротким паролем не проходит парсинг и приложение не стартует вовсе, то есть карточку видит оператор в `development`/`test`.
- Проверка: `next build` не содержит секретов (E0-10 тест — сделать постоянным CI-шагом).

**DoD:** брутфорс блокируется; заголовки проходят проверку (например, securityheaders-подобный чек локально); CI-тест на секреты в бандле зелёный.
**Оценка:** 0.5 д. **Зависимости:** E0-10.

## Вне скоупа E13

- Многопользовательский доступ, роли, SSO — SaaS-фаза.
- Внешний мониторинг/алертинг (Grafana, PagerDuty) — достаточно внутренней страницы и, при желании, Telegram-уведомлений позже.
- Логи в UI (просмотр pino-логов) — смотрим через `docker compose logs`; в UI только DLQ и алерты.
