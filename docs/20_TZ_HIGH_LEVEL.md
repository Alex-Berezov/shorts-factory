# Верхнеуровневое ТЗ — AI Shorts Factory (v1)

_Дата: 2026-09-05. Назначение: рамочный документ для декомпозиции. Каждый эпик (E0–E13) в дальнейшем разворачивается отдельной итерацией в задачи размером 0.5–2 дня._

## Как читать этот документ

- **Эпик** = крупный блок функциональности с целью, скоупом, критериями приёмки (AC) и зависимостями.
- Порядок эпиков соответствует фазам из `01_ARCHITECTURE.md` §7 и `10_SYSTEM_DESIGN.md`.
- «Вне скоупа MVP» — фиксируем сознательно, чтобы не расползаться.
- Статусы декомпозиции: ⬜ не декомпозирован / 🔄 в декомпозиции / ✅ декомпозирован. Маркер стоит в заголовке эпика; документы декомпозиции — `docs/30_E0_TASKS.md` и далее по номерам.

## Общие требования ко всем эпикам (Definition of Done)

1. Код на TypeScript strict, проходит Biome, typecheck и Vitest в CI.
2. Все фоновые операции — идемпотентные BullMQ-джобы с ретраями и логом стоимости в `api_usage_log`.
3. Все AI-ответы валидируются Zod и сохраняются версионированно (model + prompt_version + cost).
4. Секреты только в env; ничего чувствительного в web-бандле и в Git.
5. На каждый эпик — минимум smoke-тест ключевого сценария.

## E0. ✅ Каркас проекта и инфраструктура (Phase 1, фундамент)

_Декомпозиция: `docs/30_E0_TASKS.md` (13 задач, ≈11–13 дней)._

**Цель:** рабочий монорепозиторий, в котором можно разрабатывать все последующие эпики.

**Скоуп:**
- pnpm workspaces + Turborepo, базовые tsconfig/Biome/Vitest.
- Docker Compose: postgres, redis, api, worker, web; `.env.example`.
- `@sf/config`: Zod-валидация env, константы лимитов (YT units/день, Gemini $/день, TTS $/мес).
- `@sf/db`: Drizzle + первая миграция ядра схемы (таблицы из System Design §5).
- `@sf/core`: базовые доменные типы и Zod-схема Content DNA.
- apps/api: Fastify-скелет, healthcheck, error-handler, pino, отдача OpenAPI.
- apps/worker: BullMQ-скелет, регистрация очередей, DLQ, graceful shutdown.
- apps/web: Next.js-скелет, layout, basic auth, страница `/system` (заглушка).
- GitHub Actions: lint → typecheck → test → build.

**AC:** `docker compose up` поднимает всё; `pnpm dev` работает; тестовый job проходит через очередь и пишет запись в Postgres; CI зелёный.

**Зависимости:** нет.

## E1. ✅ Source Radar (Phase 1)

_Декомпозиция: `docs/31_E1_TASKS.md` (11 задач, ≈14–15 дней)._

**Цель:** автоматический мониторинг каналов-доноров и детекция аномально ускоряющихся видео.

**Скоуп:**
- CRUD tracked_channel (UI + API), резолв channelId/handle → uploads playlist.
- Cron-синк новых видео (`playlistItems.list`), фильтр Shorts, запись tracked_video.
- Снапшоты статистики по точкам 1h/3h/6h/12h/24h/48h/7d (delayed jobs) батчами `videos.list`.
- Скоринг (чистые функции в `@sf/core`): views/hour, ускорение, отношение к базлайну канала; trend_signal.
- Базлайн канала: медиана/перцентили последних N видео, автоматический пересчёт.
- Story-кластеризация: обнаружение одного сюжета на нескольких каналах (LLM-группировка заголовков/тем; pgvector — опция).
- UI «Radar»: таблица сигналов с сортировкой по score, карточка видео, ручной запуск анализа.
- Учёт YouTube-квоты + автопауза при достижении дневного лимита.

**AC:** после добавления реального канала система в течение часа подтягивает новые видео; для нового видео появляются снапшоты по расписанию; сигналы с score видны в UI; расход units виден на `/system`; search.list не используется нигде.

**Зависимости:** E0.

## E2. ✅ Video Intelligence / Content DNA (Phase 1)

_Декомпозиция: `docs/32_E2_TASKS.md` (10 задач, ≈11 дней)._

**Цель:** глубокий анализ любого публичного Short по URL → структурированная Content DNA.

**Скоуп:**
- `@sf/integrations/gemini`: клиент видеоанализа по публичному YouTube URL, структурированный вывод по полной схеме DNA (blueprint §5.2), Zod-валидация, repair-ретрай.
- Hook Analysis Pass (0–5 сек) как отдельный джоб для приоритетных видео.
- Режим анализа локального файла (для своих видео) с повышенной детализацией.
- Версионирование промптов (`prompt_version`), фиксация модели и стоимости.
- Джоб `intel.analyze-video`: ручной запуск из UI + авто для top-N сигналов (порог в настройках).
- UI: карточка DNA (транскрипт, таймлайн, hook-разбор, transferable patterns, risky-to-copy).
- Гейт по бюджету Gemini $/день.

**AC:** по кнопке на любом сигнале в течение нескольких минут появляется валидная DNA-карточка; невалидный JSON от модели не роняет пайплайн; стоимость каждого анализа видна; повторный запуск создаёт новую версию, не перетирая старую.

**Зависимости:** E0, E1 (частично можно параллельно: клиент Gemini не зависит от Radar).

## E3. ✅ Idea Inbox (Phase 1)

_Декомпозиция: `docs/33_E3_TASKS.md` (9 задач, ≈9–10 дней)._

**Цель:** ежедневная ранжированная очередь идей с решением Approve / Reject / Later за минимальное время оператора.

**Скоуп:**
- Джоб `inbox.build` (ежедневно): агрегация trend_signal + story_cluster + DNA → карточки идей со всеми полями из blueprint §5.3 (включая velocity/acceleration/cluster-скоры, «why now», предложенные хуки, целевую длительность, opportunity score).
- Ранжирование (чистая функция в core, веса в настройках).
- UI Inbox: лента карточек, кнопки Approve/Reject/Later, фильтры по статусу/категории, причина реджекта (опционально).
- Approve → автозапуск E4 (когда готов); Later — отложенная очередь с возвратом.
- Дедупликация: один сюжет не должен приходить карточкой повторно после решения (кроме существенного нового всплеска).

**AC:** утром в Inbox лежат свежие ранжированные карточки; решение по карточке — 1 клик; статусы и история решений сохраняются; повторных дублей решённых сюжетов нет.

**Зависимости:** E1, E2.

## E4. ✅ Research Agent (Phase 2)

_Декомпозиция: `docs/34_E4_TASKS.md` (8 задач, ≈9 дней)._

**Цель:** независимая фактическая проверка одобренной идеи → factual brief.

**Скоуп:**
- Джоб `research.run` после approve (и авто для top-N по настройке).
- Поиск независимых источников (LLM с web-инструментами провайдера), верификация имён/дат/чисел/последовательности событий.
- Выход: verified_claims / uncertain_claims / sources / contradictions / risk_flags (legal, copyright, safety) — по blueprint §5.4.
- Явный список «claims, допущенных в скрипт».
- UI: страница брифа при идее, ручное редактирование/подтверждение оператором.
- Статусная модель идеи: approved → in_research → researched.

**AC:** после approve в разумное время появляется бриф с разделением подтверждённого/неподтверждённого и ссылками на источники; рискованные темы помечены флагами; оператор может исключить любой claim.

**Зависимости:** E3.

## E5. ✅ Script Engine (Phase 2)

_Декомпозиция: `docs/35_E5_TASKS.md` (7 задач, ≈8.5–9 дней)._

**Цель:** мастер-скрипт на английском из factual brief + Content DNA паттернов, без клонирования конкурентов.

**Скоуп:**
- Джоб `script.generate`: 3–5 вариантов хука, мастер-скрипт по структуре hook → setup → escalation → reveal/payoff → ending, целевая длительность, CTA только при обосновании.
- Использование только допущенных claims из брифа; перенос abstract patterns из DNA, запрет near-verbatim заимствований (anti-plagiarism самопроверка промптом).
- Experiment tags скрипта (стратегия хука, структура, reveal_pct и т.д.) — совместимо с E8.
- Версионирование скриптов, хранение всех вариантов.
- UI: редактор/ревью скрипта, выбор хука, ручные правки с сохранением новой версии, кнопка «в production».

**AC:** по researched-идее генерируются валидные варианты; финальный скрипт фиксируется отдельной версией с experiment tags; правки оператора не теряются; в скрипте нет заимствованных дословных пассажей из DNA-транскриптов (выборочная проверка).

**Зависимости:** E4 (использует E2-DNA).

## E6. ✅ Production Package (Phase 2)

_Декомпозиция: `docs/36_E6_TASKS.md` (6 задач, ≈6 дней)._

**Цель:** полный производственный пакет для ручного монтажа в CapCut.

**Скоуп:**

- UI: печатабельная/копируемая страница пакета; чекбоксы выполнения; экспорт в Markdown.
- Статус идеи: scripted → in_production → ready_to_publish.

**AC:** для финального скрипта в 1 клик собирается пакет, по которому реально смонтирован хотя бы один Short; оператор отмечает выполнение пунктов.

**Зависимости:** E5.

## E7. ✅ Analytics Warehouse (Phase 3)

_Декомпозиция: `docs/37_E7_TASKS.md` (9 задач, ≈10.5–11 дней)._

**Цель:** собственная аналитика канала в своей БД.

**Скоуп:**
- Google OAuth2 offline flow (единственный пользователь), шифрованное хранение refresh token.
- Реестр own_video: привязка опубликованных Shorts к идеям/скриптам; ручное добавление для видео фазы 0.
- Ежедневный ingest YouTube Analytics API: метрики из blueprint §5.10 по видео/дню (+country где доступно), окно дозревания 3–7 дней с перезаписью.
- Ingest публичной статистики своих видео (Data API) для быстрых сигналов до дозревания аналитики.
- Фиксация auto-dub наблюдений: таблица dub_track (язык, статус, заметки о качестве) с ручным вводом на этапе ревью дабов.
- UI «Analytics»: таблица+графики по видео (24h views, AVD, avg %, retention-прокси), сравнение видео.

**AC:** после OAuth данные канала появляются в БД и дашборде; ежедневное пополнение без ручных действий; для каждого опубликованного Short видна динамика; ручной журнал фазы 0 импортируем (см. E12).

**Зависимости:** E0 (независим от E1–E6, можно делать параллельно с Phase 2).

## E8. ✅ Experiment Engine (Phase 3, mandatory)

_Декомпозиция: `docs/38_E8_TASKS.md` (10 задач, ≈11–12 дней)._

**Цель:** превращение каждого Short в структурированный эксперимент и генерация рекомендаций.

**Скоуп:**
- experiment_features для каждого own_video (полный набор из blueprint §5.11), автозаполнение из скрипта/DNA/пакета + ручное дополнение.
- Ежедневный recompute: winners vs losers (свои и конкурентские), корреляции фич с метриками, momentum тем/категорий.
- Рекомендации следующих контролируемых экспериментов с указанием уверенности (без ложной каузальности) — формат примера из blueprint §5.11.
- Планировщик экспериментов: создание experiment (гипотеза, дизайн, например 5/5 сплит), привязка будущих видео, отчёт по завершении.
- UI «Experiments»: рекомендации, активные эксперименты, история выводов.

**AC:** каждый Short имеет заполненные фичи; после ≥20–30 видео система выдаёт содержательные рекомендации с confidence; эксперимент можно завести, привязать видео и получить итоговое сравнение.

**Зависимости:** E7 (+данные E2/E5 для фич).

## E9. ✅ Localization Layer (Phase 4)

_Декомпозиция: `docs/39_E9_TASKS.md` (9 задач, ≈9.5–10 дней)._

**Цель:** управляемая локализация: учёт Auto Dubbing (Mode A) сейчас и Custom Localization Factory (Mode B) в долгую.

**Скоуп:**
- Mode A: рабочий процесс ревью авто-дабов (чек-лист по языкам, оценки качества в dub_track), сравнительная таблица языков.
- Mode B: джоб `localize.script` — локализация (не буквальный перевод) с сохранением фактов и reveal-тайминга, допуск ±2 сек; локализованные title/description/hashtags; captions (SRT/VTT); QA против factual brief.
- Матрица языков: приоритетный список 10–20 языков с конфигом стратегии на язык (auto / custom / off).
- Подготовка к Multi-Language Audio: пакет корректно именованных файлов + инструкция ручной загрузки; правило «удалить авто-даб перед загрузкой кастомного».

**AC:** по каждому опубликованному Short фиксируются оценки авто-дабов; для выбранного языка генерируется локализованный пакет (скрипт+метаданные+captions), проходящий QA-сверку фактов.

**Зависимости:** E5, E7; для загрузки кастомных дорожек — внешнее условие (Advanced Features).

## E10. ✅ Voice Factory (Phase 4)

_Декомпозиция: `docs/40_E10_TASKS.md` (9 задач, ≈10–11 дней)._

**Цель:** абстракция TTS-провайдеров и bake-off для выбора голоса по языкам.

**Скоуп:**
- Интерфейс `TtsProvider` + адаптеры: ElevenLabs, OpenAI TTS, Google Chirp 3 HD, Gemini TTS, Cartesia.
- Реестр голосов: язык → провайдер/голос/инструкции/скорость/стоимость (blueprint §5.8).
- Bake-off-раннер: один скрипт × языки × провайдеры → аудиофайлы + таблица сравнения (naturalness, emotion, pronunciation, timing, cost) с ручными оценками в UI; YouTube Auto Dub как baseline-строка.
- Генерация финальных кастомных дорожек для Mode B, QA-статусы, hard-cap бюджета TTS.

**AC:** bake-off по 2–3 языкам проведён и задокументирован в системе; для выбранного языка кастомная дорожка генерируется в 1 действие и попадает в handoff-пакет E9.

**Зависимости:** E9.

## E11. ✅ Publishing Layer (Phase 5)

_Декомпозиция: `docs/41_E11_TASKS.md` (8 задач, ≈9–9.5 дней)._

**Цель:** автоматизация публикации там, где это официально поддержано.

**Скоуп:**
- Upload/schedule через Data API (учёт 1600 units за insert), выставление original language = English, метаданные, captions.
- Публикация локализованных метаданных.
- Полуавтомат для кастомных аудиодорожек: подготовленный пакет + пошаговый чек-лист Studio (пока нет API).
- Календарь публикаций в UI (план 2/день), статусы: draft → scheduled → published.
- Автопривязка опубликованного видео к own_video/аналитике.

**AC:** Short публикуется/планируется из приложения; квота учтена; после публикации видео автоматически появляется в E7-цикле.

**Зависимости:** E6, E7.
