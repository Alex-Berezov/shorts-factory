## Цикл одной задачи

```
владелец: /auto
  0  next из трекера; продолжить in_progress, если есть
  1  start <id>; файл дела; первая задача эпика -> уточнение решений эпика (planner -> techlead/pm)
  2  planner (opus): DoD -> план в файл дела (шаги, файлы, тесты, риски, допущения, развилки, модель worker)
  3  развилки -> pm (продукт) / techlead (техника), fable; решение -> docs/DECISIONS.md сразу
  4  worker (sonnet|opus по плану): код + посадка тестом; открытые вопросы -> шаг 3 -> worker (<=2 круга)
  5  /qa: 7 ревьюеров параллельно + встроенный code-review high; таблица в файл дела
  6  блокеры -> /fix (worker) -> /qa по зонам, два круга; спор -> techlead
  7  gates.js полностью (lint, typecheck, test, build, no-search-list, tracker, harness); отметка lastGates
  8  документы: DECISIONS, ADR, приёмка эпика, TECH_DEBT, уроки
  9  commit (conventional, id в теме); push и CI - если есть origin
  10 tasks.mjs done; отчёт 8 строк; СТОП. Следующая задача - новая сессия после /clear
```

Стоп-условий шесть (`commands/auto.md`): тема владельца; красные гейты/CI после двух починок;
блокеры после двух кругов и техлида; нет внешнего предусловия; очередь пуста; замок коммита
не пускает без ослабления. Во всех - `tasks.mjs block <id> "<причина>"`, отчёт, стоп.

## Почему такие роли

- **PM и техлид вместо одного арбитра.** Владелец хочет, чтобы продуктовые вопросы решались
  строго по документации, без знания техники, а технические - с учётом продукта. Один агент
  на обе роли смешивал бы аргументы; два - дают чистое разделение и понятный журнал («PM решил
  X», «техлид решил Y»). Подагент не может позвать подагента, поэтому связку «PM, потом техлид
  с ответом PM» собирает оркестратор.
- **Worker отдельно от оркестратора.** Оркестратор на sonnet держит короткий контекст
  (координация, таблицы, решения), а код пишется в свежем контексте подагента с планом на входе.
  Это и экономия (оркестратор не таскает прочитанные файлы через весь заход), и качество
  (worker не отвлекается на ход ревью).
- **Семь ревьюеров.** Четыре из newDev (логика, данные, соглашения, тесты) плюс три под задачи
  этого проекта: безопасность (ключи внешних API, деньги), архитектура (портфолио-требование
  владельца), продукт (проигрывание DoD по коду - то, что в AVA делает `ava-review-scenario`
  и что ловит класс дефектов, невидимый чек-листам).

## Модели

| Модель | Кто | Почему |
| --- | --- | --- |
| fable | `pm`, `techlead`, `review-architecture`, `review-product` | решения вместо человека и суждение о замысле - самое дорогое место для ошибки; вызываются редко (единицы раз на задачу) и на коротком контексте |
| opus | `planner`, `review-correctness`, `review-data`, `review-security`, `worker` на рискованных задачах | глубокое чтение кода и логика; свой контекст у каждого |
| sonnet | `/auto` и остальные команды, `worker` по умолчанию, `review-conventions`, `review-tests` | дисциплина, а не глубина; дисциплину держат хуки |

Правило из «Экономия токенов - принципы»: у подагентов свой кэш - модель выбирается по
сложности честно; у команд главной сессии смена модели перечитывает всю историю по цене записи,
поэтому дорогая модель у команды стоит только там, где команда идёт первым ходом после `/clear`
(`/task` на opus). `/auto` идёт на sonnet и держит контекст коротким за счёт подагентов.
Сессию держать на одной модели (`/model sonnet`), между задачами - `/clear`.

Когда `worker` идёт на opus (решает planner в разделе «Модель исполнителя»): схема БД и
миграции, деньги и квоты, идемпотентность джобов, авторизация и секреты, конкурентность.
Правка вёрстки, текстов, конфигов, документации - sonnet.

## Замки

| Замок | Что не пускает | Как снять законно |
| --- | --- | --- |
| `standards` | добавленные строки с `any`, `console.*`, `process.env` вне config, `search.list`, относительный импорт пакета, `TODO` без id, `biome-ignore` без причины … (S01–S16, W01–W08); S13/S14 - форма роута в `apps/api/src/routes/**` (регистрация только `defineRoute`, без `.get(`/`.route(`/`withTypeProvider` на любом получателе; `defineRoute` в файле с `...errorResponses()` в коде; точные статусы - `apps/api/test/route-shape.test.ts`), S15/S16 - направление `contracts -> core`, `api-client -> contracts` по импортам (`from`, побочный `import`, `import("…")`, `require("…")`; все формы и манифесты - `test/dependency-direction.test.ts`) | починить строку; клапан `any-ok:`/`console-ok:`/`env-ok:` с причиной - и слово в отчёте |
| `commit-gate` | коммит без отметки `/qa` по этому диффу, без зелёных гейтов, с мусором, с ослаблением (W01–W09), с `--no-verify`/`--force`, не по conventional commits | сделать то, чего не хватает; обход - брак |
| `report-honesty` | «проверки зелёные» без `lastGates{code:0}` по текущему диффу; «Обвязка: не менялась» при тронутых `.claude/**` | прогнать гейты или написать правду |

Рекомендательные хуки - не замки, ничего не запирают (решение владельца 03.10.2026 в
`docs/DECISIONS.md`). `answer-length` (Stop) меряет каждый ответ, в том числе переписанный
после отказа `report-honesty`; ответ длиннее 9 непустых строк или 900 знаков прозы не
переписывается (владелец увидел бы его дважды), а замечание ложится в состояние под номером
сессии (`lengthNotes`, не больше 8 сессий, вытесняется старейшая; без `session_id` не
пишется). `remind-format` (UserPromptSubmit) отдаёт агенту только замечание своей сессии
в начале её следующего хода и снимает его; замечания других сессий не трогает. Значит,
замечание работает только в многоходовой сессии: в `/auto` за отчётом идёт `/clear`, и до
новой сессии оно не доходит - длину отчёта там держит форма `auto.md` и
`output-styles/short.md` (решение техлида 03.10.2026). На длинной сессии `remind-format`
дописывает и памятку формата.

`SF_HOOK_STATE_DIR` - служебная переменная самопроверки: `harness-selftest.js` ставит её
во временную папку на весь прогон, и хуки в пробах пишут состояние туда, а не в боевой
`.claude/.qa-state`. До первой пробы selftest снимает байты боевого файла (или отмечает,
что его нет), последняя проба сравнивает их с текущими: хук, записавший в боевой файл,
делает её красной. Пишущая в тот же файл соседняя сессия тоже даст красное - тогда прогон
повторяется. Папка убирается на выходе selftest, в том числе по Ctrl+C. Читает переменную
только `lib.js:statePath()`; в работе хуков она не задаётся.

Замков на запись файлов нет - решение владельца 06.09.2026: `protect-files` (защищённые пути,
`unlock.txt`), `scope` (рамки задачи, `scope.txt`), `diff-boundaries` (парные правки X01/X02)
и `qa-lock` (счётчик правок без `/qa`) сняты, потому что каждый запуск `/auto` останавливался
на них раньше плана. `/qa` по-прежнему обязателен перед коммитом - это держит `commit-gate`. Агент правит любые
файлы; ошибки ловят семь ревьюеров, техлид и замок коммита.

Все замки fail-closed: упавший хук отказывает и называет причину, а не молча пропускает.
Отпечаток диффа считается в одном месте (`diff-hash.js`) от списка файлов, поэтому отметки
`/qa` и гейтов переживают коммит и не открывают замок другому диффу.

## Гейты

`node .claude/hooks/gates.js` читает `rules.sf.json`:

| id | команда | когда |
| --- | --- | --- |
| lint | `pnpm lint` | всегда |
| typecheck | `pnpm typecheck` | всегда |
| test | `pnpm test` | всегда (E0-02A); повторы снимает кэш turbo |
| test:int | `pnpm test:int` | изменено то, что читают int-тесты: граф int-пакетов, корневые конфиги и `.env.test` (точный glob - гейт `test:int` в `rules.sf.json`, E0-02A); нужен поднятый Compose (`infra/docker-compose.yml`), без него красный |

Ещё - файлы, названные в `note` гейтов `compose` и `tracker`, которых нет в `when`/`cmd` самого гейта (`test/compose-rules.test.ts`, `test/container.test.ts`): проба сверяет пути `note` с диском и требует, чтобы каждый такой файл выбирал `harness-selftest`; пути из `when`/`cmd` гейта-владельца (у `tracker` - `docs/tasks/tasks.json`, `docs/00_STATUS.md`, `docs/*_TASKS.md`, `docs/TECH_DEBT.md`, `scripts/tasks.mjs`, `scripts/lib/paths.mjs`, `scripts/lib/tracker-doc.mjs`, `scripts/lib/files.mjs`) его не выбирают (E0-12F, круг 3; E0-12M). Ещё - боевые формы роута `apps/api/src/routes/health/index.ts` и `apps/api/src/routes/system/index.ts`: их читают пробы S13/S14 как пропуск, и проба требует, чтобы каждая выбирала `harness-selftest` (E0-12D). Точный glob - гейт `harness-selftest` в `rules.sf.json` |

Только полный прогон (без `--only`) ставит `lastGates`; частичный - для работы, замок его не видит.
Гейт, названный в `--only`, идёт при любом `when` (в том числе glob без совпавших файлов и `never`), причина в
`--list` - «выбран через --only» (E0-12M); на чистом дереве `--only` гонит названные гейты в каждом репозитории
`repos.json`, где они объявлены (`--repo` сужает; позиция в файле не участвует). Id ищется по гейтам всех репозиториев `repos.json`: id, которого нет ни в одном, гейт только
репозитория, куда прогон не идёт (нет изменений или `--repo` назвал другой; подсказка - `--repo=<имя>`), и
пустой `--only=` - код 1 без единого запуска.

Полный прогон из команд обвязки (`/auto`, `/qa`, `/fix`, `/gates`, `/done`) идёт инструментом Bash в фоне
(`run_in_background: true`) с ожиданием уведомления о выходе: foreground-вызов Bash снимается через 600 с, а
сумма `timeoutSec` гейтов больше (один `test:int` - до 600 с), и инструмент снял бы `gates.js` раньше предела
гейта - без имени гейта, сводки и снятия дерева. Это единственное место с доводом; команды и подсказка
`report-honesty.js` ссылаются сюда. Пробу держит `harness-selftest` («команды и report-honesty.js, которые велят
гнать gates.js, велят гнать его в фоне»: строка с вызовом или следующая называет `run_in_background: true`).

Предел: у каждого гейта поле `timeoutSec` (целое от 1 до 3600, секунды - потолок `MAX_TIMEOUT_SEC` в `gates.js`
ниже предела таймера Node 2^31-1 мс; число и его причина одной фразой - в `note` гейта: худший известный замер
x3 и больше, не меньше 60 с, E0-12M; нижнюю границу 60 с у гейтов `rules.sf.json` проверяет `harness-selftest`,
x3 от замера - нет: замер живёт в файле дела). `runGate` запускает команду асинхронным `spawn` без stdin (гейт не
интерактивен: команда, ждущая ввода, сразу получает конец ввода, а не висит до предела; на POSIX гейт ещё и в
своей сессии - `detached` это `setsid`) и по пределу снимает всё дерево процессов
(Windows - `%SystemRoot%\System32\taskkill.exe /pid <pid> /T /F`, POSIX - своя группа процессов и `SIGKILL` группе):
одной оболочки мало, `pnpm -> turbo -> next` держали бы пайп вывода. Итог - одно правило (E0-12M, D2/D3): код 0
только когда оболочка вышла с 0 и оба пайпа вывода закрылись сами, без предела и без снятия; всё остальное -
красный с фактами, без вывода о дереве из закрывшегося пайпа. Снятие подтверждено (`taskkill` с кодом 0, сигнал
группе ушёл) и вывод закрылся за 2 с - «гейт снят по пределу N с», в сводке `СНЯТ ПО ПРЕДЕЛУ N с`; снятие
отказало (нет `taskkill.exe`, его отказ, сигнал группе не ушёл) или вывод не закрылся - «гейт не завершился за
предел N с; <что ответило снятие>; <закрылся ли вывод>; снять руками», в сводке `ПРЕДЕЛ N с, СНЯТЬ РУКАМИ`; гейт
без поля или с недопустимым значением не запускается и красный («нет предела timeoutSec»). Оболочка вышла, а
вывод ещё открыт: на POSIX остаток её группы снимается сразу (номер группы не достаётся чужому, пока в ней есть
процесс) - красный «оставшиеся процессы её группы сняты»; вывод не закрылся за 2 с (Windows - см. «Известные
ограничения», POSIX - остаток сменил группу) - красный «… вывод держал оставшийся от неё процесс …; снять
руками», в сводке `ОСТАТОК ЖИВ, СНЯТЬ РУКАМИ`, код оболочки - только в тексте. Вывод
гейта в памяти - первый и последний МиБ, середина срезается со строкой «срезано N байт вывода» (срез - по границе
символа UTF-8; stdout и stderr декодируются каждый своим декодером, символ, разрезанный между кусками одного
потока, цел). Файл вывода пишется красному гейту с выводом (любой длины) и любому гейту с выводом длиннее 200
строк - его экран срезан посередине (решение техлида Р2 E0-12O от 22.10.2026, вариант A); короткий зелёный и гейт без
вывода файла не оставляют (пустой файл ничего не объясняет). Файл - в своём каталоге временного каталога
(`sf-gates/gates-<repo>-<id>-<pid>.log`; каталог 0o700, файл только владельцу - 0o600, создаётся заново, `wx`, так что
файл прошлого прогона с тем же pid не передаёт ему свои права), путь печатается под выводом: подпись «Полный
вывод: <путь>» - только когда середина не срезана, иначе «Вывод в файле - первые и последние байты, середина (N байт)
срезана». Сбой записи файла гейт не роняет: под выводом строка «Файл
вывода не записан (<код>)», пути нет, вердикт прежний. Файлы вывода `gates.js` старше недели удаляются один раз за
прогон, при первой записи, и только в `sf-gates`: остальной временный каталог не читается и не трогается; сбой чтения
каталога или удаления файла гейт не роняет. История прогонов не ведётся ни в файле, ни в `note`:
причину прошлого красного читают по файлу вывода, итог прогонов задачи - в файле дела (E0-12O, Р2; пробы selftest
«короткий красный гейт - полный вывод в файле», «короткий зелёный гейт файла вывода не оставляет», «длинный зелёный
гейт - файл вывода есть», «красный гейт без вывода файла не оставляет», «сбой записи файла вывода назван», «mode
0o600 и flag wx», «файлы вывода старше недели удалены», «каталог читается для чистки один раз за прогон», «сбой
чистки гейт не роняет»). SIGINT
(Ctrl+C), SIGTERM, SIGHUP, дошедшие до обработчика `gates.js`, снимают дерево идущего гейта, выход 130/143/129,
`lastGates` не ставится; гейт, чья оболочка уже вышла, не трогается (на POSIX его группа снята в ветке выхода,
на Windows PID чужой) - stderr называет его «оболочка уже вышла, остаток не снимается». На Windows внешний SIGTERM
(`process.kill`, снятие задачи) - TerminateProcess, до обработчика не доходит («Известные ограничения»).
Пробы `harness-selftest` - сон за предел, внук со `stdio: 'inherit'` (мёртв после возврата), вышедшая с 0 оболочка
с внуком (код 1), команда в пределе, гейт без поля, 5 МиБ кириллицы (срез без U+FFFD), символ, разрезанный между кусками
stdout с куском stderr, `gateTimeoutSec` на недопустимых значениях, поле у каждого гейта `rules.sf.json` (не меньше
60 с); `gates.js` из командной строки во временном дереве с двумя репозиториями - полный прогон со снятым и
болтливым гейтом (сводка, подпись файла вывода, код 1, `lastGates` с кодом 1), `--only` на чистом дереве (гейт
второго репозитория идёт в нём, гейт обоих - в обоих), опечатка, пустой `--only=`, гейт другого репозитория (с
`--repo` и без), гейт, читающий stdin до конца, при открытом stdin `gates.js`, SIGINT, SIGTERM, SIGHUP (коды и
снятый внук), сигнал после выхода оболочки (ни одного повторного снятия), отказ снятия по пределу при открытом и
закрывшемся выводе, снятие с ответом «успех» при открытом выводе. Жив ли
внук, проба решает по отметке, которую он пишет каждые 100 мс, а не по `process.kill(pid, 0)`: зомби на POSIX и
PID, доставшийся другому процессу на Windows, такую отметку не двигают.

Пробы выбора гейтов в `harness-selftest.js` берут `selectGates` из самого `gates.js` (`module.exports`; `main()` и `process.exit` - только под `require.main === module`), а не исполняют скрипт в `vm` (E0-12D). Что `require` не запускает гейты, не ставит `lastGates` и не зовёт `process.exit`, сторожит отдельная проба: в дочернем процессе она подменяет список изменённых файлов, запуск команд гейтов и `process.exit` и требует ноль запусков, ни одного выхода и ни одной отметки; пока она красная, пробы выбора `gates.js` не грузят. Строки пробы одного гейта начинаются с `гейт <id>:`. Пробы `standards.js` пишут файлы не в боевые `src`, а во временное дерево с копией `.claude/hooks`; последняя проба сверяет снимок дерева до и после прогона: записи `git status` с отпечатком содержимого (перезапись уже изменённого файла видна) и игнорируемые записи `!!`; новый файл внутри уже игнорируемого каталога снимок не видит (TECH_DEBT, переадресовано E0-12T), правка руками во время прогона даёт ту же красную строку. `standards.js` в дереве пробы идёт с `CLAUDE_HOOK_DEBUG=1`: исключение внутри `L.guard` хук глотает (код 0, пустой stdout - как пропуск), а с этой переменной печатает в stderr строку `hook error: …`; проба, которая читает ответ `standards.js`, на отказе и на пропуске считает красным и эту строку (`HOOK_ERROR`), и код вне 0/2. Временные git-репозитории проб не берут из машины ничего, что исполняет код: `git init --template=`, коммит с `-c core.hooksPath=<пустой временный каталог>`; снимок дерева зовёт `git -c core.fsmonitor=false status`.

## Установка и откат

После любой правки обвязки:

```powershell
powershell -ExecutionPolicy Bypass -File .claude/install.ps1
node .claude/hooks/harness-selftest.js
```

Установщик делает снимок `.claude/` в `../.claude-snapshots/` (10 последних), сверяет модели
у команд и агентов, пишет `settings.local.json` (режим разрешений `bypassPermissions` и
allow-список на `.claude/**`; режим `dontAsk` молча отклонял встроенные запросы Claude Code
на запись в `.claude/**`, и `/auto` не мог вести `.task-current`), гоняет самопроверку. Хуки подхватываются новой сессией.

Откат: правил руками и стало хуже - `git checkout -- .claude/<файл>` (обвязка в git вместе
с кодом); прогнал установщик и стало хуже - `otkat.ps1` (возвращает снимок, `settings.local.json`
в том числе). Отключить всё - убрать блок `hooks` из `.claude/settings.json`.

## Копилка уроков

`.claude/qa-index.md` - строка на урок (правило и признак в диффе), читают все ревьюеры и техлид.
`.claude/qa-lessons.md` - полная запись, открывается по номеру. Урок пишется в оба файла
шагом «Документы» `/auto` или шагом 4 `/done`. Урок, целиком выражаемый регуляркой, переезжает
в `standards` (`rules.sf.json`) и из копилки убирается: длинную копилку читают по диагонали.

## Экономия токенов (что из принципов применено)

1. Длинное - в файл дела, в чат - решения (`answer-length`, `output-styles/short.md`).
2. Чтение чужими руками: разведка у `planner`, код у `worker`, ревью у семи подагентов;
   оркестратор читает только их короткие итоги.
3. Ревьюерам - индекс уроков, не журнал.
4. Полный набор ревьюеров в автономном режиме намеренно (дифф никто не читает); сокращение
   только при ручном `/qa zones=…`.
5. Модели по ролям с оглядкой на кэш (таблица выше).
6. Одна задача на сессию, `/clear` между задачами: два контекста в одном портят план и ревью.

## Известные ограничения

- Хуки регистрируются через `${CLAUDE_PROJECT_DIR:-.}` - сессию открывать в корне репозитория.
- `test:int` требует поднятый `docker compose` (postgres, redis); без него гейт честно красный -
  это стоп-условие 4, а не повод выключить гейт.
- Два int-прогона на одной тестовой базе рвут друг друга: `resetTestDatabase` одного (`DROP SCHEMA ... CASCADE`)
  сносит таблицы под другим (E0-12O, шаг 3: 6 красных из 6 на двух одновременных `pnpm test:int`). Защита - два
  рубежа во входной проверке каждого int-пакета (оба `entry-check/*`, до первого сброса и до `assertMigrated`).
  **Замок прогона** (`packages/db/test-support/run-lock.ts`, решение техлида 22.10.2026, Р3 B): первым действием
  `setup` берётся сессионный `pg_try_advisory_lock(RUN_LOCK_KEY)` (свой ключ test-support, не ключ миграций) на
  клиенте проверки (`createProbeDb`, `application_name=sf-session-check`) и держится до `teardown` `globalSetup`
  пакета; занятый замок - отказ «another integration run holds the run lock of the test database …» с `pid`,
  `application_name`, `backend_start` держателя; зависший прогон снимают сначала по его процессу (Ctrl+C,
  процесс vitest/turbo), команда `pg_terminate_backend` в тексте - только для сессии, чей процесс уже мёртв:
  на живом прогоне она снимает его барьер, и следующий прогон сбросит базу под ним. Повтор шага 3 (а)
  после замка: второй прогон красный с этим текстом за 2-3 с, первый зелёный целиком - 3 из 3 (смещения 2, 20,
  60 с). Убитый прогон отпускает замок вместе со своей сессией; держит его только зависший процесс.
  **Замеры сессий** (`assertNoOtherTestSessions`, `packages/db/test-support/other-sessions.ts`) - второй рубеж под
  замком, для клиентов без замка (открытый `psql`/IDE, процесс от упавшего прогона): отказ на чужой клиентской
  сессии тестовой базы, видной в двух замерах `pg_stat_activity` (до 12 замеров через 250 мс; `pg_isready`,
  клиенты `sf-session-check` - замок своего прогона и проверка чужого, - бэкенд в старте и не-клиентские процессы
  не считаются), с `pid`, `application_name`, `client_addr`, `state`, `backend_start` и `pg_terminate_backend`.
  Второй прогон замеры сами не ловят: рядом с прогоном `@sf/db`, чьи файлы открывают и закрывают клиентов
  постоянно, проверка проходила в 10 из 23 моментов (замер Fix 2, файл дела E0-12O) - поэтому рубежом против
  второго прогона служит замок. Отказы чтения у обоих: молчащая база - «did not answer within N ms», недоступная -
  «cannot read the run lock / the sessions» с подсказкой про Compose, строка иной формы - отказ разбора с её
  текстом. **Окно, которое не закрыто** (флак принят с условием переоткрытия, `docs/TECH_DEBT.md`, строка гейта
  `test:int` E0-12B): замок держит пакет, а не весь `turbo run test:int` - между пакетами (`@sf/db` -> api ->
  worker, секунды на смену процесса vitest) он свободен, и второй прогон, стартовавший в этот момент, берёт его,
  а первый получает отказ замка в следующем пакете (названный красный, но уже после того, как второй начал
  сброс); Redis замок не защищает вовсе. Правило остаётся: не гонять `gates.js` рядом со своим `pnpm test:int`.
  Переоткрыть при красном `test:int` исходного класса (`relation ... does not exist`, `Hook timed out`,
  `ECONNREFUSED` на Redis) без отказа замка или «other session(s)» в начале того же прогона.
- Гейт `compose` гонит `docker compose config`: без Docker CLI он красный с текстом
  `check-compose: the docker CLI is not on PATH` - это отсутствие предусловия, а не сломанный
  Compose (сломанный файл даёт `docker compose config failed` с выводом Compose).
- Снятие гейта на Windows - `taskkill /T` по PID живой оболочки (`cmd.exe`): дерево находится по
  родителю. Оболочка вышла, а вывод держит оставшийся от неё процесс - он не снимается: PID
  вышедшей оболочки мог получить чужой процесс, а `taskkill /T` по нему снял бы чужое дерево.
  `gates.js` закрывает вывод через 2 с, гейт красный («на Windows он не снят ... снять руками»,
  в сводке `ОСТАТОК ЖИВ, СНЯТЬ РУКАМИ`, код оболочки в тексте; E0-12M, проба «оболочка вышла с 0,
  внук держит вывод»).
- `SIGKILL` самого `gates.js` (и `TerminateProcess` на Windows - так снимает процесс
  `process.kill`, снятие задачи и снятие по таймауту инструмента) перехватить нельзя: дерево идущего
  гейта остаётся. На POSIX оно в своей сессии и группе - снять `kill -KILL -<pgid>`. На Windows
  замерено 21.10.2026 (E0-12M, круг fix 2): родитель снят `process.kill`, его ребёнок и внук живы.
  `taskkill /T` по PID снятого родителя их не найдёт: найти первого живого потомка по
  `ParentProcessId` (`Get-CimInstance Win32_Process`) и снять `taskkill /T /F /PID <pid>`.
  Обработчики есть у SIGINT, SIGTERM, SIGHUP (E0-12M).
- Реальные внешние API (YouTube, Gemini, TTS) тратят деньги: агент ходит в них только для
  смоук-проверок, названных в DoD задачи, и только при ключе в `.env`; иначе блокирует задачу
  как «нет предусловия».
- `db-guard` (стража боевой базы) из newDev не перенесён: боевой базы у проекта пока нет.
  Появится VPS - завести до первого деплоя (задача E0-11/E13).
