# E1. Source Radar — декомпозиция на задачи

_Дата: 2026-09-05. Источник: `20_TZ_HIGH_LEVEL.md` (E1), `10_SYSTEM_DESIGN.md` §4, §5 (Radar), §7.1, `01_ARCHITECTURE.md` §5.1. Статус эпика: ✅ декомпозирован, реализация не начата. Зависит от E0 (`30_E0_TASKS.md`)._

## Цель эпика

Автоматический мониторинг каналов-доноров и детекция аномально ускоряющихся видео.

**AC эпика:** после добавления реального канала система в течение часа подтягивает новые видео; для нового видео появляются снапшоты по расписанию; сигналы с score видны в UI; расход units виден на `/system`; `search.list` не используется нигде.

## Внешние предусловия (делает оператор, не код)

Чек-лист H1–H2 из `02_PRE_DEVELOPMENT_CHECKLIST.md`:

1. Создать Google Cloud проект, включить **YouTube Data API v3**.
2. Создать **API key** (публичные чтения; OAuth для E1 не нужен), ограничить ключ по API (только YouTube Data API v3).
3. Записать ключ в `.env` как `YOUTUBE_API_KEY`. Квота по умолчанию 10 000 units/день, сброс в полночь по тихоокеанскому времени (PT).

Без ключа задачи E1-01…E1-04 разрабатываются на записанных фикстурах, но AC эпика без реального ключа не проверить.

## Что уже есть из скелета и E0

- `@sf/db`: таблицы `tracked_channel`, `tracked_video`, `video_stats_snapshot` (unique `(video_id, point)`), `trend_signal`, `story_cluster`, `story_cluster_video`.

## Архитектурные решения E1

Принимаем по умолчанию; E1-11 оформляет как ADR. Спорные — обсудить до старта соответствующей задачи.

1. **Снапшоты — тиком по расписанию, а не delayed-job на каждое видео.** Каждые 5 минут job `radar.snapshot` выбирает из БД все пары (video, point), у которых наступило время точки и снапшота ещё нет, и снимает их батчами до 50 id за один `videos.list` (1 unit). Delayed-job на каждую пару (как в System Design §4) не позволяет батчить и даёт тысячи отложенных задач в Redis. Идемпотентность — уникальный индекс `(video_id, point)`. Пункт §4 System Design обновлён в этой же итерации.
2. **Допуск по времени точки.** Точка `Xh` считается снятой, если снапшот сделан в окне `[X, X + допуск]`, допуск = 25 % от X (для 1h — 15 мин, для 24h — 6 ч), но не менее 10 мин. Опоздавшие точки снимаются с реальным `captured_at` и флагом `is_late`; расчёты используют фактическое время, а не номинальную точку. Видео, обнаруженное позже своей точки (например, 1h при синке раз в 60 мин), получает немедленный `adhoc`-снапшот.
3. **Детекция Shorts — эвристика по длительности.** Data API не отдаёт признак Shorts. Правило v1: `duration_sec <= 180` (лимит Shorts с октября 2024) **и** видео не является live/premiere. Порог в `app_setting` (`radar.shorts_max_duration_sec`). Проверка через редирект `youtube.com/shorts/<id>` — вне скоупа (неофициально, хрупко); каналы-доноры по определению Shorts-каналы, ложные срабатывания оператор гасит вручную.
4. **Синк новых видео — до первого известного.** `playlistItems.list` по uploads-плейлисту постранично (50 за страницу, 1 unit) до первого `yt_video_id`, который уже есть в БД. При добавлении канала — backfill последних N видео (по умолчанию 50, `radar.backfill_count`) ради базлайна; они помечаются `is_backfill = true` и не порождают сигналов.
5. **Базлайн канала — двухуровневый.** (a) `final_views`: медиана/p25/p75 просмотров видео старше 7 дней (по backfill и накопленным данным, обновляется ежедневно). (b) `curve`: ожидаемая доля финальных просмотров на каждой точке (1h…48h), по умолчанию — общая кривая-константа, после накопления ≥ 10 видео с полным набором точек — своя кривая канала. `baselineRatio(video, point) = views / (final_views.median × curve[point])`.
6. **Сигналы append-only, статус оператора — на видео.** `trend_signal` — новая строка при каждом пересчёте (история для Experiment Engine); UI показывает последнюю. Решения оператора (`ignored`, `promoted`) хранятся в `tracked_video.radar_status`, а не в сигнале.
7. **Кластеризация сюжетов — только LLM, без pgvector.** Кандидаты: видео за последние 48 часов с сигналом выше порога. Gemini (текстовая модель) группирует по заголовку + описанию + каналу, выход строго по Zod-схеме. Слияние с существующими кластерами — по пересечению видео. Эмбеддинги отложены до момента, когда объём (> 300 кандидатов за проход) сделает LLM-подход дорогим.
8. **Квота YouTube — три уровня защиты.** (a) `BudgetGuard` перед каждым вызовом сравнивает `units_today` с `YT_UNITS_DAILY_SOFT_CAP`; при превышении — пауза очередей `radar.*` и алерт в `app_setting`. (b) Ошибка `quotaExceeded` от API → немедленная пауза без ретраев. (c) Автовозобновление job'ом `system.quota-reset` в 00:05 PT. Плюс CI-тест, который падает при любом упоминании `search.list` в исходниках.

## Задачи

Формат: цель → что сделать → DoD → оценка → зависимости. Оценки в рабочих днях, суммарно ≈ 14–15 дней.

### E1-01. `@sf/youtube`: клиент Data API для публичных чтений

**Цель:** единственная точка обращения к YouTube Data API, каждая операция считает units и валидирует ответ.

**Сделать:**
- Реализовать `DataApiClient` поверх `googleapis` (`youtube('v3')`, auth = API key): `getChannel({ id | handle | username })` → `channels.list part=snippet,contentDetails,statistics`; `listPlaylistItems(playlistId, pageToken?)` → `playlistItems.list part=snippet,contentDetails maxResults=50`; `getVideos(ids[])` → `videos.list part=snippet,contentDetails,statistics,liveStreamingDetails`, автоматическая нарезка по 50 id.
- Zod-схемы ответов (`@sf/youtube/schemas`) — нормализованные типы `ChannelInfo`, `PlaylistItem`, `VideoDetails` (парсинг ISO-8601 duration → секунды, флаг live/premiere по `liveStreamingDetails`).
- Учёт units по `QUOTA_COST` через `UsageLogger` из `@sf/core` **до** возврата результата; `jobId` пробрасывается в лог.
- Ошибки: `YoutubeQuotaExceededError` (403 `quotaExceeded`), `YoutubeNotFoundError`, `YoutubeApiError`; ретраи только на 5xx/сетевые (3 попытки, экспоненциально), никаких ретраев на 403/404.
- Фикстуры: записать реальные ответы (после получения ключа) в `test/fixtures/*.json`, юнит-тесты на маппинг и подсчёт units с подменённым транспортом.
- CI-тест `no-search-list.test.ts`: grep по `packages/` и `apps/` на `search.list` / `youtube.search` — падает при находке (решение 8c).

**DoD:** все три метода работают против реального ключа (ручная проверка скриптом `pnpm --filter @sf/youtube smoke -- @handle`); юнит-тесты зелёные; каждая операция даёт строку в `api_usage_log`.
**Оценка:** 1.5 д. **Зависимости:** E0-05, E0-09.

### E1-02. Каналы: парсинг ввода, резолв, CRUD, API и контракты

**Цель:** оператор добавляет канал любой ссылкой или handle, система сама находит uploads-плейлист.

**Сделать:**
- Чистая функция `parseChannelInput(str)` в `@sf/core`: `https://youtube.com/@handle`, `@handle`, `https://youtube.com/channel/UC…`, `UC…`, `youtube.com/c/name`, `youtube.com/user/name` → `{ kind: handle | id | username, value }`; юнит-тесты на все формы и мусор.
- Репозиторий `trackedChannelRepo`: `create/update/list/get/softDeactivate`, уникальность `yt_channel_id`.
- Контракты `@sf/contracts/radar/channels`: `POST /radar/channels { input }` → резолв через E1-01, сохранение, постановка первого синка + backfill (E1-03); `GET /radar/channels` (с агрегатами: видео всего, за 7д, последний синк, ошибка); `PATCH /radar/channels/:id { isActive }`; `DELETE` — деактивация (данные не удаляем, сигналы — история).
- Обработка ошибок: канал не найден → 404 с понятным текстом; дубликат → 409 с ссылкой на существующий.
- Тесты роутов через `app.inject` с подменённым `DataApiClient`.

**DoD:** добавление канала по `@handle` и по URL создаёт запись с `uploads_playlist_id`; повторное добавление — 409; тесты зелёные.
**Оценка:** 1 д. **Зависимости:** E1-01, E0-06, E0-07.

### E1-03. Job `radar.sync-channels`: новые видео, фильтр Shorts, backfill

**Цель:** новые Shorts каналов-доноров появляются в `tracked_video` не позже одного интервала синка.

**Сделать:**
- Repeatable-job `radar.sync-channels` (интервал из `radar.sync_interval_min`) ставит дочерние job'ы `radar.sync-channel` по каждому активному каналу; `jobId = radar.sync:<channelId>:<floor(now / interval)>` (решение 5 из E0).
- Процессор канала: `BudgetGuard.assert("youtube_data")` → постранично `listPlaylistItems` до первого известного `yt_video_id` (решение 4; максимум `radar.backfill_count` для нового канала, максимум 3 страницы для регулярного синка — защита от квоты) → `getVideos` по новым id → фильтр Shorts (решение 3) → insert `tracked_video` (`is_backfill` для первого синка) → `last_synced_at`.
- Для каждого нового не-backfill видео: немедленный `adhoc`-снапшот из уже полученной `statistics` (без лишнего вызова) и постановка `radar.score`.
- Не-Shorts видео **не сохраняем** (только счётчик в логе), чтобы не раздувать таблицу.
- Ошибки канала (удалён, приватный плейлист) → `last_sync_error`, канал не деактивируется автоматически, алерт видно в UI.
- Ручной запуск: `POST /radar/channels/:id/sync` и `POST /radar/sync` (все).
- Интеграционный тест с фейковым `DataApiClient`: первый синк = backfill N, второй синк = только новые, третий без изменений = 1 unit.

**DoD:** на реальном канале первый синк подтягивает последние N Shorts, следующий — только новые; повторный запуск в том же интервале игнорируется по `jobId`; `api_usage_log` показывает ожидаемое число units.
**Оценка:** 1.5 д. **Зависимости:** E1-02, E0-08.

### E1-04. Job `radar.snapshot`: тик, выбор due-точек, батч-снапшоты, недоступные видео

**Цель:** каждое отслеживаемое видео получает снапшоты 1h/3h/6h/12h/24h/48h/7d с минимальным расходом квоты.

**Сделать:**
- Чистые функции в `@sf/core`: `duePoints(publishedAt, takenPoints, now, tolerance)` → список точек к съёму с флагом `late`; `pointWindow(point)` — границы допуска (решение 2); юнит-тесты на границы, опоздания, будущие точки.
- Repeatable-job `radar.snapshot` каждые `radar.snapshot_tick_min` минут: запрос к БД — активные видео моложе 7д + допуск, без снапшота на наступивших точках; батчи по 50 → `getVideos` (part `statistics` достаточно — уточнить, что `part` не влияет на стоимость) → insert снапшотов (`ON CONFLICT (video_id, point) DO NOTHING`), `last_snapshot_at`.
- Видео, не вернувшиеся в ответе (удалено/приватно) → `is_available = false`, дальше не снимаем.
- После записи — постановка `radar.score` на каждое видео с новым снапшотом (payload: `videoId`, `point`).
- Оценка расхода в логе job'а: сколько видео, сколько батчей, сколько units.
- Интеграционный тест: три видео с разным возрастом → правильные точки и один батч; повторный тик ничего не снимает.

**DoD:** на реальных данных за сутки у нового видео появляются точки 1h…24h (с учётом допусков); расход units за тик ≤ ceil(видео/50); тесты зелёные.
**Оценка:** 1.5 д. **Зависимости:** E1-03.

### E1-05. Базлайн канала: расчёт, backfill, ежедневный пересчёт

**Цель:** у каждого канала есть ожидание «нормальных» просмотров по возрасту видео, чтобы отличать всплеск от обычного размера канала.

**Сделать:**
- Zod-схема `ChannelBaselineSchema` в `@sf/core`: `{ finalViews: { median, p25, p75, n }, curve: Record<point, share>, curveSource: 'default' | 'own', computedAt }`.
- Чистые функции: `percentiles(values)`, `buildCurve(snapshotsByVideo)` (медиана долей `views(point)/views(7d)` по видео с полным набором), `expectedViews(baseline, point)`; юнит-тесты, включая случай `n < 5` (базлайн `insufficient`, ratio не считаем).
- Кривая по умолчанию `radar.baseline_curve_default` в `app_setting` (стартовые значения — консервативная экспертная оценка, помечена как таковая; заменяется собственной после накопления данных).
- Backfill при добавлении канала: `statistics` из E1-03 для последних N видео → `finalViews` сразу (видео старше 7д).
- Repeatable-job `radar.baseline` раз в сутки: пересчёт `finalViews` (все видео канала старше 7д, окно — последние 100) и `curve` (решение 5); запись в `tracked_channel.baseline_stats`.
- Тест: канал с 12 видео с полными снапшотами → `curveSource = own`; с 3 видео → `default`.

**DoD:** после добавления реального канала `baseline_stats` заполнен в течение минуты; через сутки job пересчитал без ошибок; тесты зелёные.
**Оценка:** 1 д. **Зависимости:** E1-04.

### E1-06. Job `radar.score` и `trend_signal`

**Цель:** каждому снапшоту соответствует числовой сигнал, по которому можно сортировать и фильтровать.

**Сделать:**
- Расширить `@sf/core/scoring`: `computeSignal({ snapshots, publishedAt, baseline, point, weights })` → `{ viewsPerHour, acceleration, baselineRatio | null, score }`; `viewsPerHour` берётся между двумя последними снапшотами (или от `publishedAt`, если снапшот один), `acceleration` — при трёх и более; при отсутствии базлайна вес `baselineRatio` перераспределяется на остальные; юнит-тесты на 1/2/3+ снапшота, нулевые интервалы, отрицательный рост.
- Процессор `radar.score` (payload `videoId`, `point`; `jobId = radar.score:<videoId>:<point>`): читает снапшоты и базлайн, считает, вставляет `trend_signal` (append-only, решение 6).
- Веса из `app_setting.radar.weights`, кэш 60 с.
- Порог «заметного» сигнала `radar.signal.min_score` — используется E1-07 и UI-фильтром «только значимые».
- Миграция полей `trend_signal` (см. таблицу изменений схемы).

**DoD:** для видео с 3+ снапшотами сигнал содержит все четыре величины; пересчёт с изменёнными весами даёт новую строку, старая сохраняется; тесты зелёные.
**Оценка:** 1 д. **Зависимости:** E1-05.

### E1-07. Job `radar.cluster`: LLM-группировка сюжетов

**Цель:** один сюжет, разошедшийся по нескольким каналам, виден как одна сущность с общим моментумом.

**Сделать:**
- `LlmClient` в `@sf/gemini` (текстовые запросы, `responseSchema` JSON-mode, Zod-валидация, один repair-ретрай, учёт токенов и $ через `UsageLogger`, `promptVersion` обязателен) — общий интерфейс, который потом используют E2 (частично), E3–E5.
- Промпт `radar.cluster` v1 в `prompt_version`: вход — список `{ videoId, channel, title, description[:300], publishedAt }` кандидатов + список активных кластеров `{ clusterId, label, summary }`; выход по Zod: `{ assignments: [{ videoId, clusterId | null }], newClusters: [{ label, summary, videoIds }] }`. Инструкция: один сюжет = одно реальное событие/история, а не общая тема.
- Процессор (cron 3 раза в день, `jobId` по слоту): кандидаты — видео за `radar.cluster.window_h` часов с последним `score >= radar.cluster.min_score`, ещё не в кластере, плюс активные кластеры; `BudgetGuard.assert("gemini")`; применение результата: `story_cluster_video`, `channel_count`, `momentum = { sumViewsPerHour, maxScore, channelCount, videoCount, updatedAt }` (Zod-схема в core), `status = faded`, если ни одного нового видео за 72 ч.
- Ограничение размера запроса: не более 150 кандидатов за вызов, остальное — следующим проходом.
- Тесты: чистая функция слияния результата LLM с существующими кластерами (пересечение видео, конфликтующие назначения); интеграционный тест с фейковым `LlmClient`.

**DoD:** на реальных данных за 48 ч один и тот же сюжет с двух каналов оказывается в одном кластере (ручная проверка на 5–10 примерах); стоимость каждого прохода видна в `api_usage_log`; невалидный ответ модели не роняет job (repair → DLQ).
**Оценка:** 2 д. **Зависимости:** E1-06, E0-09.

### E1-08. Квота YouTube: автопауза, автовозобновление, алерты

**Цель:** проект никогда не упирается в лимит квоты неожиданно и восстанавливается сам.

**Сделать:**
- Расширить `BudgetGuard` (E0-09): при `units_today >= soft cap` → `pauseQueues(["radar.*"])` + `app_setting.alerts.youtube_quota = { pausedAt, unitsToday, reason }` (решение 8a).
- Обработка `YoutubeQuotaExceededError` в `defineJob`: job фейлится без ретраев, очереди `radar.*` ставятся на паузу, алерт с `reason = api_quota_exceeded` (8b).
- Repeatable-job `system.quota-reset` в 00:05 PT (cron с TZ `America/Los_Angeles`): снять паузу, очистить алерт, записать событие в лог (8c). Ручное снятие паузы — `POST /system/queues/:name/resume` (используется и `/system` в E13).
- `/system/status` дополняется: прогноз расхода units до конца дня (линейная экстраполяция), состояние паузы, время до сброса.
- Тесты: юнит на экстраполяцию и порог; интеграционный — записать расход выше cap → job синка не делает внешний вызов и очередь на паузе.

**DoD:** искусственно заниженный soft cap останавливает Radar без ошибок в DLQ, алерт виден на `/system`; после сброса очереди возобновляются автоматически.
**Оценка:** 1 д. **Зависимости:** E1-03, E0-09.

### E1-09. API сигналов, видео и кластеров (контракты + роуты)

**Цель:** всё, что нужно UI Radar, доступно типизированными эндпоинтами.

**Сделать:**
- `GET /radar/signals`: последний сигнал на видео, фильтры `channelId`, `minScore`, `maxAgeH`, `status`, `onlyShorts` (по умолчанию да), сортировка `score | viewsPerHour | acceleration | publishedAt`, пагинация курсором; ответ включает видео (title, thumbnail, channel, publishedAt), сигнал, `clusterId`.
- `GET /radar/videos/:id`: видео + все снапшоты + история сигналов + кластер + `radar_status` + список `video_analysis` (пусто до E2).
- `PATCH /radar/videos/:id { radarStatus }` (`ignored | promoted | new`).
- `GET /radar/clusters` (активные, сортировка по моментуму) и `GET /radar/clusters/:id` (видео кластера).
- `POST /radar/videos/:id/analyze` — ставит `intel.analyze-video` (процессор реализует E2; до E2 job лежит в очереди `waiting` — это ожидаемо, документировать).
- Все схемы — в `@sf/contracts/radar/*`, клиент `@sf/api-client` расширен; тесты роутов через `app.inject` на сид-данных.

**DoD:** OpenAPI на `/docs` показывает все роуты Radar; сортировка/фильтры покрыты тестами; клиент типизирован.
**Оценка:** 1 д. **Зависимости:** E1-06 (сигналы), E1-07 (кластеры) — кластерную часть можно делать параллельно с E1-07 по контракту.

### E1-10. UI «Radar»: каналы, таблица сигналов, карточка видео, кластеры

**Цель:** оператор за минуту видит, что ускоряется, и запускает анализ в один клик.

**Сделать:**
- `/radar/channels`: форма добавления (ввод любой формы из E1-02, ошибки 404/409 инлайн), таблица каналов (видео всего/7д, последний синк, ошибка, базлайн-медиана, тумблер активности), кнопка «Синк сейчас».
- `/radar`: таблица сигналов с сортировкой по колонкам, фильтрами (канал, возраст, min score, статус, «только значимые»), бейдж кластера; строка — миниатюра, заголовок (ссылка на YouTube), канал, возраст, views/h, ускорение, ×базлайн, score; действия в строке: «Игнорировать», «В приоритет», «Анализировать».
- `/radar/videos/[id]`: карточка — превью, метаданные, график просмотров по снапшотам (Recharts, точки помечены номинальными точками и `late`), история сигналов, кластер со списком «соседей», кнопка «Анализировать», блок «Content DNA» (заглушка «появится после E2» с состоянием job'а).
- `/radar/clusters`: список активных кластеров с моментумом и видео внутри.
- Данные через `@sf/api-client` из server components, мутации — через route handlers Next; ревалидация 30 с.
- Пустые состояния (нет каналов / нет сигналов ещё) с подсказкой, что делать.

**DoD:** сценарий «добавить канал → через час увидеть новое видео в таблице → открыть карточку → увидеть снапшоты и сигнал → нажать Анализировать» проходит вручную; UI не делает прямых запросов в API из браузера.
**Оценка:** 2 д. **Зависимости:** E1-09, E0-10.

### E1-11. Обкатка на реальных каналах, тюнинг, документация

**Цель:** Radar подтверждён на реальных данных, параметры имеют осмысленные значения, решения зафиксированы.

**Сделать:**
- Добавить 5–10 реальных каналов-доноров (список — в `app_setting`-независимом документе `docs/50_SOURCE_CHANNELS.md`, ведёт оператор).
- 48–72 часа наблюдения: расход units/день (цель < 1 500), доля опоздавших точек, распределение score, качество кластеров (5–10 ручных проверок), ложные Shorts.
- Тюнинг `radar.weights`, `radar.signal.min_score`, `radar.cluster.min_score`, интервалов; результаты и обоснование — в этом документе (раздел «Приёмка»).
- ADR для решений 1–8; обновить `10_SYSTEM_DESIGN.md` §4 (тиковые снапшоты, `radar.baseline`, `system.quota-reset`) и §5 (изменения схемы).
- Прогон AC эпика, заполнение таблицы приёмки, статусы в `20_TZ_HIGH_LEVEL.md`, `CLAUDE.md`.

**DoD:** все AC выполнены и отмечены; параметры зафиксированы с обоснованием; документы обновлены.
**Оценка:** 1 д (размазан по 2–3 календарным дням наблюдения). **Зависимости:** E1-10.

## Порядок и параллелизм

```text
E1-01 ─► E1-02 ─► E1-03 ─┬─► E1-04 ─► E1-05 ─► E1-06 ─┬─► E1-07 ─┐
                         │                            │          ├─► E1-09 ─► E1-10 ─► E1-11
                         └─► E1-08 ───────────────────┴──────────┘
```

- E1-08 (квота) можно начинать сразу после E1-03, параллельно со снапшотами.
- E1-09 стартует по контракту после E1-06; кластерные роуты добавляются, когда готов E1-07.
- `LlmClient` из E1-07 — общий с E2; если E2 декомпозируется параллельно, владелец `LlmClient` — E1-07, E2 переиспользует.
- Работа над E2 (клиент Gemini для видео) не зависит от E1 и может идти параллельно начиная с E1-04.

## Вне скоупа E1 (сознательно)

- Запуск анализа DNA по сигналу — кнопка и job ставятся здесь, обработка — E2.
- Автоматический анализ top-N сигналов — E2 (порог в настройках).
- Эмбеддинги / pgvector для кластеров — только если LLM-подход станет дорогим.
- Проверка Shorts через редирект `youtube.com/shorts/<id>` — неофициально, не берём.
- Комментарии/лайки как отдельные сигналы — собираем в снапшоты, в score v1 не входят.
- Уведомления (Telegram/email) о сильных сигналах — после E3 (Inbox их и так соберёт).

## Приёмка (заполняется при закрытии эпика)

| AC | Как проверяем | Статус |
|---|---|---|
| Новое видео реального канала подтягивается в течение часа | добавить канал, дождаться публикации/следующего синка, проверить `tracked_video` и UI | ⬜ |
| Снапшоты появляются по расписанию | у нового видео за сутки есть точки 1h…24h с учётом допусков; доля `is_late` < 20 % | ⬜ |
| Сигналы с score видны в UI | `/radar` сортируется по score, карточка показывает историю | ⬜ |
| Расход units виден на `/system` | цифра за день совпадает с суммой `api_usage_log`; прогноз и состояние паузы отображаются | ⬜ |
| `search.list` не используется | CI-тест `no-search-list` зелёный | ⬜ |
| Расход < 1 500 units/день при 5–10 каналах | наблюдение 3 дня | ⬜ |
